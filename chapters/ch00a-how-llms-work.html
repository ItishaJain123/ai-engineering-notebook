Part 1 · Chapter 1

How LLMs Actually Work

General AI Eng tokens, embeddings, and the transformer — explained with zero jargon first

Why this matters. You've been using Claude for a while now without knowing what's happening under the hood — and that's totally fine for building things. But once you know how the model actually turns your prompt into a reply, a bunch of "weird" behaviors stop being mysterious: why it sometimes hallucinates, why longer prompts cost more, why it can "forget" things from earlier in a long chat, why it's bad at counting letters in a word. This chapter is the missing foundation.

The one-sentence version

An LLM is a very, very good next-word guesser. That's it. Give it some text, and it predicts — one word-piece at a time — what's statistically most likely to come next, based on patterns it saw in a huge amount of text during training. Do that thousands of times in a row, feeding each guess back in as new input, and you get a paragraph, an essay, or code.

1. It doesn't see words — it sees "tokens"

Before any of the "smart" stuff happens, your text gets chopped into small pieces called tokens. A token is usually a word, part of a word, or a punctuation mark — not always a whole word.

Text: "unbelievable pizza!" Tokens: [ "un" | "believ" | "able" | " pizza" | "!" ] IDs: [ 359 | 8271 | 822 | 12045 | 0 ] ← just numbers to the model

Why chop words into pieces instead of using whole words? Two reasons: (1) there'd be millions of possible whole words/names across every language — too many to handle efficiently, and (2) breaking rare words into familiar pieces (like un + believ + able) lets the model handle words it's never seen before, the same way you can guess "unfrogable" is about frogs even though it's not a real word.

Try it yourself: this is why Claude is sometimes bad at "how many letters are in strawberry?" — it never actually sees the letters s-t-r-a-w-b-e-r-r-y. It sees 1–2 tokens that represent the whole chunk "strawberry." Spelling-out-loud is not what the model was optimized to do.

Here's roughly what tokenization looks like in code (this is a simplified idea, not the real algorithm):

// Real tokenizers use a learned algorithm (Byte-Pair Encoding / BPE),
// but conceptually: build a vocabulary of common chunks, then
// greedily match the longest known chunk at each position.
function toyTokenize(text, vocab) {
  const tokens = [];
  let i = 0;
  while (i < text.length) {
    let match = text[i]; // fallback: single character
    for (let len = 8; len >= 1; len--) {
      const piece = text.slice(i, i + len);
      if (vocab.has(piece)) { match = piece; break; }
    }
    tokens.push(match);
    i += match.length;
  }
  return tokens;
}

This is also literally what you're paying for and budgeting when we talk about "tokens" in Chapter 7 (context management) and Chapter 20 (cost optimization) — every token in your prompt and every token in the reply costs money and counts against the context window.

2. Each token becomes a list of numbers ("embedding")

Computers don't understand the word "cat" — they understand numbers. So every token gets converted into a long list of numbers (usually hundreds to thousands of them) called an embedding or vector. Think of it as coordinates that place the word in a giant "meaning space."

Analogy: imagine a huge 3D map where similar things are placed near each other — "cat" and "dog" are close together (both pets), "cat" and "kitten" are even closer, and "cat" and "spreadsheet" are far apart. A real embedding isn't 3 dimensions, it's hundreds of dimensions, but the idea is identical: closeness in this space = closeness in meaning.
"king" → [ 0.91, -0.22, 0.05, ... ] (e.g. 1536 numbers) "queen" → [ 0.89, -0.19, 0.44, ... ] "pizza" → [-0.12, 0.77, -0.61, ... ] king is close to queen in this space, far from pizza. Famous trick: king − man + woman ≈ queen (the math of meaning!)

This is the exact same idea used in Chapter 21 (Embeddings Deep-Dive) for RAG/search — a search engine that finds documents "similar in meaning" to your question is just measuring distance between embedding vectors.

3. The transformer: every word "looks at" every other word

Now for the actual engine: the transformer architecture. Its key trick is called attention — for every token, the model asks "which other tokens in this text are relevant to understanding me right now?" and weighs them accordingly.

Analogy: imagine reading the sentence "The trophy didn't fit in the suitcase because it was too big." To know what "it" refers to (the trophy? the suitcase?), you unconsciously glance back at earlier words and weigh them by relevance. Attention is that glancing-back process, done mathematically, for every single word, looking at every other word, simultaneously.
Sentence: "The trophy didn't fit in the suitcase because it was too big" Attention weights for the word "it": The ░░ trophy ████████████████ ← strongly attends to "trophy" didn't ░░ fit ███ suitcase ██████ ← some attention here too because ░ it (itself) was ░ too ░ big ██ ← "big" hints it's the trophy, not the suitcase

A transformer stacks many of these attention layers on top of each other (often dozens), each one refining the model's understanding a little more, mixed with simple "feed-forward" math layers in between.

Input tokens → Embeddings │ ▼ ┌─────────────────────────┐ │ Attention layer #1 │ "who should I pay attention to?" │ Feed-forward layer #1 │ "process that information" └─────────────────────────┘ │ ▼ ...repeat N times (often 32, 64, 96+ layers)... │ ▼ ┌─────────────────────────┐ │ Attention layer #N │ │ Feed-forward layer #N │ └─────────────────────────┘ │ ▼ Probability over "what token comes next?" e.g. { "pizza": 0.41, "sushi": 0.22, "salad": 0.09, ... }

4. Putting it together: one token at a time

The model doesn't write your whole answer in one shot. It predicts one next token, adds it to the text, and runs the entire process again on the new, slightly longer text — over and over — until it decides to stop.

Step 1: "I love" → predicts → "eating" Step 2: "I love eating" → predicts → "pizza" Step 3: "I love eating pizza" → predicts → "." Step 4: "I love eating pizza." → predicts → <stop>

This is why streaming responses (Chapter 18) look the way they do — you're literally watching this loop happen live, one token at a time. It's also why longer replies take proportionally longer: each token requires a full pass through the whole network.

Key takeaways

  • Tokens, not words or letters, are the model's smallest unit — this explains token costs and "letter counting" failures.
  • Embeddings turn tokens into numbers that encode meaning as position in space — the same concept powers RAG/search (Ch. 21).
  • Attention lets every token weigh every other token's relevance — this is what lets the model resolve context like pronouns.
  • The model generates one token at a time, feeding its own output back in as input — this is why responses stream token-by-token.
  • None of this is Claude-specific — every modern LLM (GPT, Gemini, Llama) is built on this same transformer idea.
🎯 Your exercise
  1. Take the sentence "The animal didn't cross the street because it was too tired." — which word does "it" refer to? Now change "tired" to "wide" — does the answer flip? This is exactly the kind of attention-weighing the model does.
  2. Open any Claude conversation and ask it to spell a long unusual word backwards, one letter at a time. Notice how it can struggle — now you know why (tokens, not letters).
  3. Reflect: why would doubling the length of your prompt roughly increase both cost and response time?
Understanding check
  1. What is a token, and why isn't it the same as a word? The smallest chunk of text the model processes — often a word-piece, chosen so the model can represent any word (even unseen ones) from a manageable-sized vocabulary of common pieces.
  2. What does "attention" let the model do? For every token, decide how much to weigh every other token when interpreting it — e.g. resolving what a pronoun refers to.
  3. Why does the model generate text one token at a time instead of all at once? Each next-token prediction depends on everything generated so far, so it re-runs the whole model on the growing sequence at every step.
