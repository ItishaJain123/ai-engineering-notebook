Multi-Agent Systems

General AI Eng when one agent isn't enough — several specialists working together

Why this matters. So far, "agent" meant one model in a loop with some tools (Ch. 19, Ch. 28). A multi-agent system is several of those working together, each with its own job, its own tools, and its own prompt. You already met a version of this with subagents (Ch. 10) — this chapter gives you the general patterns for how multiple agents coordinate, communicate, and hand off work, and — crucially — when the added complexity is actually worth it.

🟢 In plain words. A multi-agent system splits a big job across several specialized agents instead of one agent doing everything. Usually one "orchestrator" breaks the task into pieces, hands them to "worker" agents, then combines their results. It helps when a job has clearly separable parts — but every agent is another set of model calls, so it costs more.
🔍 The tricky part, in plain language. A multi-agent system isn't magic — it's just several LLM calls with a coordinator deciding who does what and passing messages between them. The orchestrator reads the goal, splits it into subtasks, sends each to a worker (a focused prompt or agent), and merges the answers. The "communication" is literally text: one agent's output becomes another's input — there's no shared brain. Picture a manager assigning tickets to specialists and stitching their work into one deliverable. The catch: coordination has overhead — more calls, more latency, more places to go wrong — so it only pays off when subtasks are genuinely independent and benefit from specialization. Takeaway: use multiple agents when a task cleanly decomposes into parallel or specialized parts; a single well-prompted agent is cheaper and simpler for everything else.

Real-world analogy

One agent is a freelancer doing everything themselves. A multi-agent system is a small company: a manager takes the request and delegates, a researcher digs up facts, a writer drafts, an editor reviews. Each person is better because they focus on one thing — but now you also need someone coordinating them, and meetings (communication) cost time. That trade-off is the entire subject of this chapter.

1. Why split into multiple agents at all?

ReasonWhat it buys you
SpecializationEach agent has a tight, focused prompt and only the tools it needs — sharper and more reliable than one agent juggling everything.
Clean contextA researcher can churn through 50 documents; only its summary reaches the writer — the writer's context stays uncluttered (the same win as subagents in Ch. 10).
ParallelismIndependent subtasks (research three topics at once) can run at the same time instead of one after another.
MaintainabilityFix or upgrade the "reviewer" without touching the "researcher" — smaller, testable pieces.
Read this before you build one. Multi-agent adds real cost: more model calls (more money + latency), more places to fail, and harder debugging. Default to a single agent. Only split when a task has genuinely distinct skills or needs true parallelism. A single well-prompted agent beats a tangled committee of five almost every time.

2. The two core patterns

Orchestrator / worker (supervisor)

One orchestrator agent owns the goal. It breaks the task into pieces and hands each to a specialized worker, then combines their results. Workers don't talk to each other — everything flows through the boss. This is the most common, most controllable pattern.

┌─────────────────┐ │ ORCHESTRATOR │ (plans, delegates, combines) └───┬────────┬────┘ delegate │ │ delegate ┌──────▼─┐ ┌──▼───────┐ ┌──────────┐ │researcher│ │ writer │ │ reviewer │ └────┬─────┘ └────┬─────┘ └────┬─────┘ └── results ──┴─────────────┘ ▲ back to orchestrator → final answer

Network / peer-to-peer

Agents talk to each other directly, deciding among themselves who handles what — no central boss. More flexible, but far harder to predict and debug (this is essentially the experimental "Agent Teams" idea from Ch. 10). Use it rarely, and only when a rigid hierarchy genuinely can't express the workflow.

Orchestrator / workerNetwork / peer-to-peer
ControlHigh — one boss decides everythingLow — emergent, harder to steer
DebuggabilityClear (trace flows through the boss)Hard (many-to-many chatter)
Best forMost real systemsOpen-ended, exploratory tasks

3. How agents actually communicate

Agents don't share thoughts — they pass messages (text, or structured data). Three questions define any multi-agent design:

  • What gets passed? Usually a compact result, not raw work. The researcher sends a 5-line summary, not all 50 documents — this is the "clean context" win. Passing everything defeats the purpose.
  • Who decides the next agent? In orchestrator/worker, the boss routes (often the model itself picks the next worker by name). In a network, each agent decides where to hand off.
  • When does it stop? You must define a clear finish condition ("reviewer approves" or "max 5 hand-offs"), or agents can ping-pong forever, burning tokens.
Handoff = a routing decision, not magic. Concretely, a "handoff" is just: the current agent's output includes which agent goes next, and the orchestration code routes control there. In LangGraph (Ch. 28) each agent is a node, and the edges between them are the communication protocol.

4. A supervisor loop, in pseudocode

// each specialist is its own ReAct agent (Ch. 28), with its own tools
const researcher = createReactAgent({ llm: model, tools: [webSearch] });
const writer     = createReactAgent({ llm: model, tools: [] });
const reviewer   = createReactAgent({ llm: model, tools: [] });

// the supervisor's ONLY job: read progress, name who goes next
async function supervisor(state) {
  const decision = await model.invoke(
    `Conversation so far:\n${state.log}\n\n` +
    `Reply with ONE word — researcher, writer, reviewer, or DONE.`
  );
  return { next: decision.content.trim() };
}

// route based on the supervisor's choice; each worker loops back to it
function route(state) {
  return state.next === "DONE" ? END : state.next;
}
// graph: START → supervisor → (worker) → supervisor → ... → END

That's the whole idea: a small routing brain, a set of specialists, and edges that always return to the router until it says DONE. Everything else is refining prompts and tools per worker.

5. The failure modes to design against

  • Infinite loops — two agents keep handing back to each other. Fix: a hard hand-off cap.
  • Context bloat — agents forward each other everything, so the shared log explodes. Fix: pass summaries, not raw work.
  • Cost blow-up — five agents each making several model calls can be 10× the cost of one. Fix: measure, and collapse agents that don't earn their keep.
  • Lost-in-translation — the writer misreads the researcher's summary. Fix: structured hand-offs (agree on a format) instead of free-form prose.
  • Diffuse responsibility — when it goes wrong, no single agent "owns" the error. Fix: prefer the orchestrator pattern where the boss is accountable.

6. Single agent vs. multi-agent — the decision

Prefer a single agent when…Consider multi-agent when…
The task is one coherent jobThe task splits into clearly distinct skills
Steps depend on each other in sequenceSubtasks are independent (can parallelize)
You want easy debugging & low costOne agent's context gets overwhelmed by everything
Latency and simplicity matter mostSpecialization measurably improves quality
The engineer's mantra. Start with one agent. Add a second only when you can name the specific problem it solves. Complexity is a cost you pay on every request, forever — make each agent earn its seat.

Key takeaways

  • A multi-agent system is several focused agents — each with its own prompt, tools, and job — coordinating on one task.
  • The benefits are specialization, clean context, parallelism, and maintainability; the costs are money, latency, and harder debugging.
  • Orchestrator/worker (one boss delegates) is controllable and the right default; network/peer-to-peer is flexible but hard to steer.
  • Agents coordinate by passing messages — send compact results, decide who's next, and always define a clear stop condition.
  • Default to a single agent. Only split when a task has genuinely distinct skills or needs true parallelism — complexity must earn its place.

Understanding check
  1. What is the main difference between the orchestrator/worker and network patterns? In orchestrator/worker, one central agent delegates and combines results (high control, easy to debug); in a network, agents talk directly and decide among themselves (flexible but hard to steer and trace).
  2. Why should you pass summaries rather than raw work between agents? To keep each agent's context clean and costs down — forwarding everything defeats the whole point of splitting the work and bloats the shared log.
💬 Conceptual questions (the kind interviewers ask)

Interviewers use multi-agent questions to check that you weigh coordination cost, not just add agents for their own sake. Answer each out loud before peeking.

  1. A single agent handles your task fine. Why might splitting it into five agents make things worse?
    Each agent is its own set of model calls, so you multiply cost and latency, and add coordination points where information gets lost or garbled between hand-offs. Multi-agent shines only when subtasks are genuinely separable; otherwise it's overhead for no benefit.
  2. In an orchestrator/worker setup, what actually flows between agents?
    Plain text (or structured messages). One agent's output is stuffed into another's prompt as input — there's no shared memory. So the orchestrator must pass enough context for each worker to succeed, and every hand-off adds tokens.
  3. Where does latency come from in a multi-agent system, and how do you cut it?
    Sequential hand-offs — each agent waits on the previous one. If subtasks are independent, run the workers in parallel instead of in a chain, then merge; that collapses many sequential calls into roughly one round's worth of wall-clock time.
  4. What's a failure mode unique to multi-agent systems, and how do you contain it?
    Errors compound across hand-offs — a worker's wrong or hallucinated output becomes the next agent's "fact" and propagates silently. Contain it by validating each agent's output (schemas, checks) before passing it on, and by making the orchestrator sanity-check results rather than blindly merging them.
