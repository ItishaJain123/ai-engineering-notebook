Vector Stores

General AI Eng where all those embeddings actually live, and how they get searched fast

Why this matters. Once you've embedded your chunks (Ch. 16) and split your documents sensibly (Ch. 17), you need somewhere to actually put millions of vectors — and a way to ask "which 5 of these are closest to my query vector?" in milliseconds. A regular SQL WHERE clause can't do that efficiently at scale. That's the entire job of a vector store.

Real-world analogy

Picture a librarian who doesn't shelve books alphabetically — instead, she organizes the whole library by "which books feel similar to this one," clustering related ideas physically near each other. Hand her any book and she can point you to the 5 most similar ones out of a million almost instantly, because she never has to walk the entire library — she just knows which section to check. A vector store is that librarian, and its smart shelving system is what makes the instant answer possible.

1. Why you can't just use a normal database query

Finding the "closest" vectors to a query means comparing your query vector against every single stored vector using something like cosine similarity (Ch. 16) — that's an exact nearest-neighbor search. It works fine for a few thousand vectors, but at millions of vectors, comparing against every single one for every single query becomes far too slow for a live application.

2. Approximate nearest neighbor (ANN) search

Vector stores solve this with ANN (approximate nearest neighbor) algorithms — most commonly HNSW (Hierarchical Navigable Small World graphs). Instead of checking every vector, ANN builds an index structure that lets the search "hop" toward the right neighborhood quickly, skipping most of the dataset. The tradeoff: you might occasionally miss the single mathematically-closest vector in favor of one that's 99% as good — a tiny accuracy cost for a massive speed win. For nearly all retrieval-augmented generation use cases, that tradeoff is a clear win.

Exact search (brute force): query ──compare──▶ vector 1 ──compare──▶ vector 2 ──compare──▶ vector 3 ... ──compare──▶ vector 5,000,000 ← too slow at scale ANN search (e.g. HNSW): query ──▶ [jump to likely neighborhood] ──▶ [refine] ──▶ top-k results (touches a small fraction of the vectors, nearly as accurate)

4. Upserting and querying — illustrative shape

Exact APIs differ, but nearly every vector store follows the same basic shape: upsert a vector with an ID and metadata, then query with a vector and a topK. This example is generic pseudocode-ish JS/TS — treat it as illustrative of the pattern, not any one provider's exact API.

// 1. Upsert a vector with metadata attached
await store.upsert({
  id: "doc-42-chunk-3",
  vector: embedding,   // e.g. [0.021, -0.184, ...] from Ch. 16
  metadata: {
    source: "handbook.pdf",
    section: "Refunds",
    publishedAt: "2024-11-02",
    userId: "team-acme"
  }
});

// 2. Query for the top-k nearest neighbors
const results = await store.query({
  vector: queryEmbedding,
  topK: 5,
  filter: {
    userId: "team-acme",
    publishedAt: { $gte: "2024-01-01" }
  }
});

// results: [{ id, score, metadata }, ...] sorted by similarity

5. Metadata filtering — why it matters

Storing metadata alongside each vector (document source, publish date, owning user, tags, etc.) turns pure "find similar things" into "find similar things that also match these constraints." Without it, you're stuck doing similarity search over your entire index and filtering results yourself afterward — wasteful, and you risk returning fewer than topK usable results after filtering. With metadata filtering pushed into the query itself, you can ask for "find similar and published after 2024 and owned by this user" in a single fast call — essential for any multi-tenant or access-controlled RAG system.

6. When to choose what

Decision guide:
  • Already on Postgres, modest scale → pgvector
  • Prototyping locally, want zero friction → Chroma
  • Need serious filtering/performance and want to self-host → Qdrant
  • Want zero ops and are fine paying for managed infrastructure → Pinecone

Key takeaways

  • A vector store's job is fast similarity search over millions of vectors — something a normal SQL query can't do efficiently.
  • ANN algorithms (e.g. HNSW) trade a tiny bit of accuracy for a massive speed win over exact nearest-neighbor search.
  • pgvector, Chroma, Qdrant, and Pinecone each fit a different point on the setup-complexity vs. ops-ownership spectrum.
  • Storing metadata alongside vectors lets you combine similarity search with hard filters like date, source, or user.
  • The right choice depends on your existing stack, scale, and how much infrastructure you want to manage yourself.
