Prompt Caching

General AI Eng stop paying full price to re-process the same large context on every request

Why this matters. Real agents and apps often send a large, mostly-unchanging block of context on every single request — a big system prompt, a full codebase, a long document, tool definitions. Without caching, you pay full processing cost and latency for that same content, over and over, on every turn. Prompt caching fixes both.

Real-world analogy

Imagine a tutor who has to re-read your entire 200-page textbook from scratch before answering every single question you ask, even if you asked five questions in a row. Prompt caching is the tutor keeping a bookmark and a mental summary of everything they already read — so the next question only costs them the time to read your new question, not the whole book again.

1. How it works: cache breakpoints

You mark a point in your prompt (a "cache breakpoint") up to which the content is unlikely to change between requests — typically after a long system prompt, a big document, or tool definitions. The API stores an internal representation of everything up to that point. On a later request with the same prefix, it reuses that stored representation instead of reprocessing it from scratch.

Request 1: ┌───────────────────────────────┐┌──────────────┐ │ Big system prompt + doc (10K ││ "Summarize │ │ tokens) — CACHE BREAKPOINT ► ││ section 3" │ └───────────────────────────────┘└──────────────┘ full cost to process this → + small cost Request 2 (same doc, new question, within cache lifetime): ┌───────────────────────────────┐┌──────────────┐ │ Same 10K tokens — CACHE HIT ✓ ││ "Summarize │ │ (reused, not reprocessed) ││ section 5" │ └───────────────────────────────┘└──────────────┘ cheap + fast → + small cost

2. What it looks like in code

const response = await client.messages.create({
  model: "claude-sonnet-5",
  max_tokens: 500,
  system: [
    {
      type: "text",
      text: hugeSystemPromptWithFullCodebaseContext, // e.g. 15,000 tokens
      cache_control: { type: "ephemeral" },           // mark cache breakpoint here
    },
  ],
  messages: [
    { role: "user", content: "What does the auth middleware do?" },
  ],
});
// response.usage shows cache_creation_input_tokens (first call)
// or cache_read_input_tokens (subsequent calls) — cached reads are
// billed at a fraction of the normal input token price

3. When caching helps (and when it doesn't)

Good fit for cachingNot a good fit
Large, stable system prompt reused across many requestsA prompt that's different on every single call
Agent with a big set of tool definitions (Ch. 11) sent every turnShort prompts where the content itself is cheap already
Multi-turn chat over one large document (RAG context, codebase)One-off requests that won't be repeated
High-volume production traffic hitting the same context repeatedlyLow-volume or highly personalized-per-request content
Cache lifetime: cached content expires after a short period of inactivity (on the order of minutes) — it's meant for active, repeated use within a session or burst of requests, not long-term storage. It's not a database; it's a short-lived processing shortcut.

4. Prompt caching vs. semantic caching — don't confuse these

Prompt caching (this chapter)Semantic caching
What's cachedThe model's internal processing of an exact, repeated prompt prefixEntire past responses, looked up by meaning-similarity (embeddings) of the question
Match requirementExact prefix match"Close enough" question, even if worded differently
Built into the API?Yes — a native Claude API featureNo — you build it yourself with an embedding lookup (Ch. 16, 19) in front of your app
RiskLow — it's still generating a real, fresh responseHigher — a "similar enough" cached answer might not actually fit the new question

Key takeaways

  • Prompt caching stores the processed representation of a repeated prompt prefix, avoiding full reprocessing cost/latency on later requests.
  • You mark a cache breakpoint with cache_control: { type: "ephemeral" }, typically after large stable content (system prompt, docs, tool defs).
  • Best fit: large, stable context reused across many requests (agents, chat over one document, high-volume traffic).
  • Cached content is short-lived (minutes), not a persistent store — it's a processing shortcut, not a database.
  • Don't confuse it with semantic caching, which caches whole responses by question similarity and you build yourself.

Understanding check
  1. What does a cache breakpoint mark? The point up to which prompt content is stable/repeated across requests, so the API can reuse its processed representation instead of reprocessing from scratch.
  2. How is prompt caching different from semantic caching? Prompt caching requires an exact repeated prefix and is a native API feature; semantic caching matches by question similarity via embeddings and is something you build yourself.
