MCP — Model Context Protocol

General AI EngClaude Code build a server from scratch · connect it to Claude Code

🟢 MCP in plain English (read this first)

Claude is smart, but by itself it's stuck in a box — it can only talk. It can't check the weather, read your database, or send an email on its own. To let it actually do things, you give it tools (like handing a helper a phone and a calculator).

MCP is just a standard way to plug a tool into an AI. That's the whole idea.

The phone-charger analogy 🔌: phones used to have a different charger each — total mess. Then USB-C gave us one plug shape that works with everything. MCP is USB-C for AI tools:

  • An MCP server = the device (a weather checker, a database reader).
  • The AI app (Claude Code) = the laptop you plug it into.
  • Both speak MCP (the same "plug shape"), so they just work together.

Tiny example: you write a little program that knows how to check the weather and announce "I offer a tool called get_weather." You plug it into Claude Code. Now when you ask "what's the weather in London?", Claude uses that tool and gives you a real answer — instead of "I can't check live weather."

Remember 3 things: (1) AI alone can only talk — tools let it do things. (2) MCP is a standard "plug shape" for connecting tools to AI. (3) Build the tool once → reuse it in any AI app.

Everything below (stdio, JSON schema, config files) is just how you build the plug. Skim it — it clicks once you build one in the exercise.

Why this matters (the technical version). An LLM can only do what its tools let it do. Before MCP, every app wired up integrations in its own bespoke way — N apps × M tools = chaos. MCP is an open standard (from Anthropic, now widely adopted) so any AI client can talk to any tool through one protocol. Build an MCP server once; it works in Claude Code, the desktop app, and other MCP clients.

Real-world analogy

MCP is the USB-C of AI tools. Before USB-C, every device had its own cable. Now one standard port fits everything. An MCP server is a device (a database, GitHub, your file system); the MCP client (Claude Code) is the laptop. As long as both speak MCP, they connect — no custom cable.

The mental model

  • Host / Client = the AI app (Claude Code). It discovers and calls capabilities.
  • Server = your program exposing capabilities.
  • A server exposes three kinds of things:
    • Tools — actions the model can call (e.g. create_issue). Most common.
    • Resources — read-only data the client can fetch (e.g. a file, a row).
    • Prompts — prewritten prompt templates the user can invoke.
  • Transport = how they talk: stdio (local process, most common for CLI) or HTTP/SSE (remote).

Build a minimal MCP server in JavaScript

We'll expose one tool: add_numbers. Uses the official SDK over stdio.

// 1) Setup
mkdir weather-mcp && cd weather-mcp
npm init -y
npm install @modelcontextprotocol/sdk zod
# add "type":"module" to package.json for ES imports
// server.js
import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import { z } from "zod";

const server = new McpServer({ name: "math-mcp", version: "1.0.0" });

// Register a tool: name, schema, handler
server.registerTool(
  "add_numbers",
  {
    title: "Add numbers",
    description: "Add two numbers and return the sum.",
    inputSchema: { a: z.number(), b: z.number() }
  },
  async ({ a, b }) => ({
    content: [{ type: "text", text: String(a + b) }]
  })
);

// Start over stdio (Claude Code launches this process and pipes JSON-RPC)
const transport = new StdioServerTransport();
await server.connect(transport);

Three things every tool needs: a name, an inputSchema (so the model knows what args to send — validated for you), and a handler that returns a content array. This mirrors the raw tool-use shape you'll meet in Chapter 11.

Connect it to Claude Code

Register the server (writes to your MCP config):

claude mcp add math -- node /abs/path/to/weather-mcp/server.js

Or add it to .mcp.json in the project (shareable with the team):

{
  "mcpServers": {
    "math": { "command": "node", "args": ["./weather-mcp/server.js"] }
  }
}

Then verify inside Claude Code with /mcp — you should see math connected and the add_numbers tool available. Ask Claude to "add 21 and 21 using the math tool."

Debug tip: stdio servers must keep stdout clean — it's the JSON-RPC channel. Never console.log to stdout in a stdio server; log to console.error (stderr) instead, or you'll corrupt the protocol.

⭐ Raw API tool use vs. MCP — the main difference

People treat these as rivals; they're not at the same layer. Hold it this way:

  • Raw API tool use (function calling) is a feature of a single API call. In your app you describe some tools in JSON; the model replies "call getWeather('London')"; then your own code runs that function and returns the result. The tools live inside your application — only that app can use them.
  • MCP is a protocol — a standardized client/server contract. The tools live in a separate server process that any MCP client (Claude Code, the desktop app, your SDK agent) can discover and call. Write the server once, reuse it everywhere.
Analogy: raw API tool use is an appliance hardwired into one house. MCP is a USB device — plug the same one into any computer.
Raw API tool useMCP
What it isA feature of one API requestA client–server protocol
Where tools liveInside your app's codeIn a standalone server
Who executes the toolYour appThe MCP server
Reuse across appsNo — locked to your appYes — any MCP client
Tool discoveryYou hardcode the tool listClient asks the server "what do you offer?"
The punchline: MCP is usually built on top of raw API tool use. An MCP client still relies on the model's function-calling ability under the hood — MCP just standardizes where tools come from and how they're delivered, making them portable instead of bespoke. So it's not "API or MCP" — it's "handle tools myself in one app" vs. "expose tools through a standard any app can reuse." (You'll build raw tool use directly in Chapter 11.)

🟢 "AI vs. MCP" — the question people actually mean to ask

"AI vs MCP" isn't really a fair fight — the AI is the brain, MCP is a plug for its hands. They're different layers, not alternatives. But there is a real, useful comparison hiding inside that question: "should the AI just wing it itself (e.g. by clicking around a website), or should it use an MCP tool built for the job?" That's the comparison worth learning.

Think of it as: doing a task yourself by hand vs. using a proper tool for it.
  • AI acting alone / driving a browser (Chapter 7's "Claude in Chrome") = a person walking into a kitchen with no recipe, reading the menu on the wall, and cooking it themselves by trial and error. Works anywhere, even with no instructions — but slow, and easy to knock something over.
  • AI using an MCP tool = calling the restaurant and ordering exactly what you want by name. Fast, precise, and the restaurant (the tool) does the actual work correctly every time.

Worked example: using GitHub with Claude

Say you want Claude to manage issues on your GitHub repo. You have two real options:

  1. Log into GitHub in Chrome and let Claude click around the website — the Claude in Chrome approach from Chapter 7.
  2. Connect a GitHub MCP server that talks straight to GitHub's API.

Both technically "work." Here's why the MCP wins almost every time:

Claude in Chrome (clicking GitHub.com)GitHub MCP server
How it worksLooks at the page, finds buttons, clicks, screenshots, repeatsCalls GitHub's API directly: "give me all open issues"
Speed for 20 issues20 rounds of screenshot → find button → click → waitA handful of direct calls, no screenshots
Token cost (Ch. 2)High — every screenshot is expensiveLow — just structured data
ReliabilityBreaks when GitHub redesigns a button/pageStable — talks to the underlying data, not pixels
SafetyHas your whole logged-in account; a malicious page could try to trick it (prompt injection, Ch. 26)Uses a scoped token — e.g. "read issues only," can't delete a repo even by mistake
Use when…No API exists, or it's a quick one-off, or you need a visual checkAn API exists — which GitHub has, so use it
The rule that ties it all together: if a clean tool/API already exists for the job (like GitHub's), give Claude an MCP tool for it — faster, more reliable, and you can limit exactly what it's allowed to do. Only fall back to driving a browser by hand (Chapter 7) when no API exists for that website.

Key takeaways

  • MCP is an open standard so any AI client can use any tool ("USB-C for AI").
  • Servers expose tools (actions), resources (read-only data), prompts (templates).
  • Transport is usually stdio locally; keep stdout clean (log to stderr).
  • A tool = name + input schema + handler returning a content array.
  • Register with claude mcp add … or a project .mcp.json; verify with /mcp.
  • Choose MCP for reusable integrations; raw tool-use for one locked-in app.
  • API vs. MCP: raw API tool use = tools live in your app, your code runs them (one app only). MCP = tools live in a standalone server any client can reuse. MCP is usually built on top of function calling.
  • "AI vs. MCP" really means "should Claude wing it by hand (drive a browser) or use a proper tool built for the job?" — prefer an MCP tool whenever one exists; it's faster, more reliable, and safely scoped (e.g. a read-only GitHub token vs. full account access in Chrome).
