Observability & Tracing

General AI Eng seeing what your AI actually did in production — so you can debug and improve it

Why this matters. Once your app is live, a user says "it gave me a wrong answer" — and you have no idea what happened. Which prompt was sent? What did retrieval return? Which tools did the agent call? How many tokens, how much money, how slow? Observability is instrumenting your app so every one of those questions has an answer. It's the eyes and ears of a production LLM system, and it feeds directly back into your evals (Ch. 33).

Real-world analogy

Observability is the flight recorder (black box) of your AI app. A plane doesn't just fly — it continuously records altitude, speed, and every control input, so that if anything goes wrong you can replay exactly what happened. Without the recorder, you're left guessing after a crash. A trace is one flight's full recording; observability is having recorders on every flight.

1. Why LLM apps are extra hard to debug

  • Non-deterministic — you often can't reproduce the bad output by re-running; you need the record of that run.
  • Many hidden steps — one user question can trigger retrieval, several tool calls, and multiple model calls (Ch. 28, 29). The failure could be in any of them.
  • The prompt is dynamic — templates, memory, and retrieved context assemble a different prompt every time. You need to see the actual text sent.
  • Cost & latency are invisible by default — without instrumentation you won't know a feature is burning money until the bill arrives.

2. The three pillars (borrowed from classic observability)

PillarWhat it capturesLLM example
LogsDiscrete events with detail"Prompt X sent, response Y received, 1,240 tokens"
MetricsNumbers aggregated over timeAvg latency, tokens/request, error rate, daily spend
TracesThe full step-by-step path of one requestretrieve → model call → tool call → model call → answer

3. Tracing — the star for LLM apps

A trace is the complete story of a single request, broken into nested spans (each step is a span). This is what lets you open one bad response and see exactly where it went wrong.

TRACE: "What's your refund policy?" total: 3.2s · 2,910 tok · $0.014 │ ├─ span: retrieve (Part 4) 0.4s │ query → top-4 docs [policy.md, faq.md, ...] │ ├─ span: model call #1 1.1s · 1,200 tok │ prompt = system + context + question │ → model decides to call get_order_status │ ├─ span: tool call: get_order_status 0.3s │ → { status: "shipped" } │ └─ span: model call #2 1.4s · 1,710 tok → final answer shown to user
This is the debugging superpower. When an answer is wrong, the trace shows whether retrieval fetched the wrong docs, the prompt was assembled badly, a tool returned junk, or the model reasoned poorly — each is a different fix. Without the trace you can only guess which.

4. What to capture on every request

CaptureWhy
The exact prompt sentThe dynamic, fully-assembled text — the #1 thing you need to debug a bad answer
The raw model responseIncluding tool-call requests and any refusals
Retrieved contextWhich chunks/docs were fed in (for RAG faithfulness checks)
Token counts & costInput/output tokens per call → track spend and find expensive paths (Ch. 20)
Latency per stepFind the slow span (often retrieval or a chained call)
Errors & guardrail tripsWhat failed and how often (Ch. 30)
User/session & feedbackTie a trace to a thumbs-down so you can learn from it
⚠️ Careful what you log. Traces capture raw prompts and responses — which often contain PII. Apply the redaction and retention rules from Ch. 32 to your traces too, or your debugging tool becomes a compliance liability.

Instrumenting is usually lightweight — many tools auto-capture once you wrap your client or set a couple of env vars. The hard part isn't collecting data; it's looking at it regularly.

6. The virtuous loop: observe → eval → improve

PRODUCTION traffic │ (observability captures real traces) ▼ spot bad responses / thumbs-down │ ▼ add them to your EVAL set (Ch. 33) │ ▼ fix prompt / retrieval / model, re-run evals │ ▼ ship the improvement ──▶ back to production
This is how mature AI products get better. Observability turns real failures into eval cases; evals turn fixes into measured gains. The two chapters are one loop — that loop is the core discipline of running AI in production.

Key takeaways

  • Observability = instrumenting your app so you can answer "what did the AI actually do?" for any production request.
  • LLM apps are hard to debug (non-deterministic, many hidden steps, dynamic prompts) — you need the record of that specific run.
  • The three pillars are logs, metrics, and traces; a trace (nested spans) is the star — it replays one request end to end.
  • Capture the exact prompt, model response, retrieved context, tokens/cost, latency, and errors — and redact PII in your traces (Ch. 32).
  • Observability feeds evals: real failures become eval cases, closing the observe → eval → improve loop.

Understanding check
  1. What's the difference between a metric and a trace? A metric is a number aggregated over many requests (avg latency, daily spend); a trace is the full step-by-step record of one single request, letting you replay exactly what happened.
  2. Why is capturing the exact assembled prompt so important? Because the prompt is built dynamically from templates, memory, and retrieved context — it's different every time — so to debug a bad answer you must see the actual text that was sent, not the template.
