Streaming

General AI Eng showing the response as it's generated, instead of making users stare at a blank spinner

Why this matters. Remember from Chapter 0a: the model generates one token at a time. Without streaming, your app waits for all of those tokens before showing anything — for a long response, that can be a 10-30 second blank wait. Streaming sends each token (or small batch of tokens) to your UI the moment it's generated, which is why every modern AI chat interface shows text appearing progressively.

Real-world analogy

Non-streaming is like ordering a meal and the waiter disappears into the kitchen until the entire multi-course meal is plated, then brings it all out at once. Streaming is a waiter bringing each dish out the moment it's ready — you start eating (reading) immediately, and the kitchen (model) is still working in the background.

1. What's happening under the hood: Server-Sent Events (SSE)

Streaming APIs use a technique called SSE (Server-Sent Events) — a long-lived HTTP connection where the server pushes small chunks of data ("events") to the client as they become available, instead of one request/response.

Non-streaming: Client ──request──▶ Server Client ◀── (wait 15s) ──── Server [entire response, all at once] Streaming (SSE): Client ──request──▶ Server Client ◀── event: "The" ─── Server Client ◀── event: " model" ─ Server Client ◀── event: " generates" ── Server Client ◀── event: " token" ─ Server Client ◀── ... continues until done ... Client ◀── event: [DONE] ── Server

2. Streaming in code

const stream = client.messages.stream({
  model: "claude-sonnet-5",
  max_tokens: 1000,
  messages: [{ role: "user", content: "Write a short poem about the ocean." }],
});

// Fires every time a new text chunk ("delta") arrives
stream.on("text", (textDelta) => {
  process.stdout.write(textDelta); // or: append to your UI element
});

stream.on("end", () => {
  console.log("\n\n[stream complete]");
});

const finalMessage = await stream.finalMessage(); // full assembled response

3. Event types you'll see

EventWhat it carries
message_startThe response is beginning — includes metadata like the model used
content_block_deltaA small chunk of new content (a few tokens of text, or a tool-input fragment)
content_block_stopA content block (a text section or tool call) has finished
message_deltaMetadata updates, like the stop reason
message_stopThe entire response is complete

4. Streaming with tool use — it gets trickier

When a model streams a tool call (Chapter 11), the tool's input arguments arrive incrementally as partial JSON fragments, not as one clean object. Most SDKs handle the buffering/reassembly for you, but it's worth knowing: you generally can't act on a streamed tool call until you've received the full content_block_stop for it — you need the complete, valid JSON before you can safely execute the tool.

5. When streaming matters (and when it doesn't)

Streaming helps a lotStreaming matters less
Chat UIs — users perceive the app as much fasterBackend batch jobs with no one watching in real time
Long-form generation (articles, long code files)Very short responses (a single word, a classification label)
Anything where perceived latency matters more than total timeStructured-output extraction (Ch. 9) you need fully parsed before use anyway
Important nuance: streaming improves perceived latency (time to first visible token), not total generation time — the model still takes the same amount of time to generate all the tokens. It's a UX win, not a raw speed win.

Key takeaways

  • Streaming sends the response token-by-token as it's generated (via Server-Sent Events), instead of waiting for the whole thing.
  • It's a perceived-latency win, not a total-generation-time win — the model doesn't finish any faster.
  • Watch for events like content_block_delta (new content chunk) and message_stop (fully done).
  • Streamed tool calls arrive as partial JSON — wait for the block to fully close before executing the tool.
  • Best for chat UIs and long-form generation; less relevant for backend jobs or short structured outputs.
