Deployment Patterns

General AI Eng the production plumbing that keeps your AI app fast, reliable, and affordable under real traffic

Why this matters. Everything so far makes a good AI app. This final chapter makes it a dependable one. Real production traffic is unforgiving: providers rate-limit you, calls occasionally fail or time out, latency spikes, and costs balloon. Deployment patterns are the well-worn techniques — retries, fallbacks, rate-limit handling, caching, streaming — that keep your app standing when things go wrong. This is the last mile between a working prototype and something users can actually rely on.

Real-world analogy

Think of a restaurant kitchen at dinner rush. One great chef (your model) isn't enough — you need a queue system for orders (rate limiting), a backup plan when an ingredient runs out (fallbacks), dishes remade when they come back wrong (retries), and appetizers sent out fast so diners aren't staring at an empty table (streaming). Deployment patterns are the kitchen's operating procedures under pressure.

1. Retries — handle the calls that fail

Network blips, provider hiccups, and transient 429/500 errors are normal at scale. Don't crash — retry, but do it politely with exponential backoff (wait a bit, then longer, then longer) so you don't hammer a struggling provider.

async function callWithRetry(fn, max = 3) {
  for (let attempt = 0; attempt < max; attempt++) {
    try {
      return await fn();
    } catch (err) {
      if (!isRetryable(err) || attempt === max - 1) throw err;
      const wait = 2 ** attempt * 1000 + Math.random() * 250;  // backoff + jitter
      await sleep(wait);
    }
  }
}
Two rules. (1) Only retry retryable errors — a rate-limit or timeout, yes; a "bad request" won't fix itself. (2) Add jitter (a little randomness) so many clients don't all retry in sync and stampede the provider at the same instant.

2. Rate limits — stay under the ceiling

Providers cap how many requests/tokens per minute you may send. Exceed it and you get 429 Too Many Requests. Handle it on both ends:

  • React: on a 429, back off and retry (§1). Providers often send a Retry-After hint — respect it.
  • Prevent: throttle your own outgoing calls with a queue or token-bucket limiter so you rarely hit the ceiling in the first place.
  • Scale up: for real production volume, request higher limits from the provider ahead of launch.

3. Fallbacks — a plan B when the primary path fails

FailureFallback
Primary model is down / overloadedRoute to a secondary model (or a different provider)
Big model too slow or rate-limitedDrop to a smaller, faster model for that request
The model call fails entirelyReturn a safe cached answer or a graceful "try again shortly" message
Degrade gracefully. A slightly worse answer beats an error page. Design the failure path deliberately — decide now what happens when the model is unreachable, rather than showing users a stack trace later.

5. Managing secrets & config

  • API keys in env vars / a secrets manager — never hard-coded, never committed to git.
  • Prompts & model IDs as versioned config — so you can change a prompt or bump the model without redeploying code, and roll back if evals drop (Ch. 33).
  • Separate staging & production keys and environments — test changes safely before real users see them.

6. Rolling out changes safely

Model and prompt changes are risky because behavior can shift subtly. Ship them the same careful way you'd ship any production change:

  • Run your eval set first (Ch. 33) — never ship a change that regresses your scores.
  • Canary / gradual rollout — send the new version to 1% → 10% → 100% of traffic, watching metrics (Ch. 34) at each step.
  • A/B test when you're unsure — compare two versions on live traffic before committing.
  • Keep rollback easy — config-driven prompts/models mean reverting is one setting, not a redeploy.

  • ☑ Secrets secured, config versioned, safe rollout plan

Key takeaways

  • Production traffic will hit failures, rate limits, and cost/latency pressure — deployment patterns keep the app standing anyway.
  • Retry transient failures with exponential backoff + jitter; only retry errors that can actually succeed on a second try.
  • Handle rate limits both ways: back off when you hit them, and throttle proactively so you rarely do.
  • Fallbacks (secondary model, smaller model, cached/graceful response) let you degrade gracefully instead of erroring out.
  • Ship changes safely: eval-gate, canary rollout, easy rollback — and use the readiness checklist to confirm you've covered all of Part 6.
