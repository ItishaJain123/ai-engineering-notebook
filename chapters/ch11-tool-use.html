Tool Use / Function Calling

General AI Eng giving a model the ability to actually do things, not just talk about them

Why this matters. Everything up to this chapter has been about getting good text out of a model. Tool use is what turns a model into an agent — something that can look up live data, run calculations, call your APIs, or take actions in the world. It's also the foundation both MCP (Ch. 4) and the agent loop (Ch. 14) are built on top of.

Real-world analogy

Without tools, the model is a very knowledgeable person locked in a room with no phone or internet — they can only answer from memory, which might be outdated or simply not contain what you need (today's weather, your account balance). Tool use is handing them a phone with a specific set of numbers they're allowed to call: "call this number to check weather," "call this number to look up an order." They decide when to make a call and what to say, but you control which calls are possible.

1. How it works: a request-response round trip

The model doesn't execute code itself — it can only request that a tool be called, with specific arguments. Your code is what actually runs the tool and hands the result back.

1. You send a prompt + a list of available tools (with schemas) │ ▼ 2. Model decides it needs a tool, replies with a "tool_use" block: { name: "get_weather", input: { city: "Austin" } } │ ▼ 3. YOUR CODE runs the actual function — the model never executes anything │ ▼ 4. You send the tool's result back to the model as a "tool_result" │ ▼ 5. Model uses that result to write its final answer to the user

2. Defining a tool

A tool definition is just a name, a description (this is what the model reads to decide when to use it — write it carefully), and a JSON Schema describing its arguments.

const tools = [{
  name: "get_weather",
  description: "Get the current weather for a city. Use this whenever " +
               "the user asks about weather, temperature, or conditions.",
  input_schema: {
    type: "object",
    properties: {
      city: { type: "string", description: "City name, e.g. 'Austin'" },
      units: { type: "string", enum: ["celsius", "fahrenheit"] },
    },
    required: ["city"],
  },
}];

3. The full round trip in code

let messages = [{ role: "user", content: "What's the weather in Austin?" }];

let response = await client.messages.create({
  model: "claude-sonnet-5",
  max_tokens: 500,
  tools,
  messages,
});

// Check if the model wants to use a tool
const toolUse = response.content.find(b => b.type === "tool_use");
if (toolUse) {
  const result = await getWeather(toolUse.input.city, toolUse.input.units);

  // Append the model's tool request AND our result, then call again
  messages.push({ role: "assistant", content: response.content });
  messages.push({
    role: "user",
    content: [{ type: "tool_result", tool_use_id: toolUse.id, content: JSON.stringify(result) }],
  });

  response = await client.messages.create({ model: "claude-sonnet-5", max_tokens: 500, tools, messages });
}
console.log(response.content[0].text); // final answer, informed by the tool result

This is exactly the mechanism the agent loop (Chapter 14) repeats over and over for multi-step tasks — this chapter is the single-round-trip building block.

4. Writing good tool descriptions

The model chooses tools based almost entirely on the description text. A vague description ("does stuff with dates") leads to the model either never using it, or using it at the wrong times. Be as specific as you'd be briefing a new employee: what it does, when to use it, and any constraints.
WeakBetter
"Searches things""Searches the internal knowledge base for product documentation. Use for questions about how our product works, not general web facts."
"Sends email""Sends an email to a specified address. Only use after explicit user confirmation of the recipient and content — never send automatically."

5. Error handling

Tools fail — APIs time out, inputs are invalid, records don't exist. Send errors back to the model as a tool_result too (marked as an error), so it can decide how to recover, instead of crashing your whole pipeline.

try {
  const result = await callExternalApi(toolUse.input);
  messages.push({ role: "user", content: [
    { type: "tool_result", tool_use_id: toolUse.id, content: JSON.stringify(result) }
  ]});
} catch (err) {
  messages.push({ role: "user", content: [
    { type: "tool_result", tool_use_id: toolUse.id, content: `Error: ${err.message}`, is_error: true }
  ]});
  // model sees the error and can retry, ask the user, or pick a different tool
}

6. Tool use vs. MCP — quick refresher

Tool use is the underlying mechanism; MCP (Chapter 4) is a standard packaging format for tools so they're portable across different AI apps, instead of hardcoded into one codebase. Every MCP tool call ultimately becomes a tool-use round trip like the one above.

Key takeaways

  • Tool use is a request-response round trip: model requests a tool call, your code executes it, you send the result back.
  • The model never executes code itself — it only decides when and how to ask for a tool call.
  • Tool descriptions are what the model uses to decide when to reach for a tool — write them like you're briefing a new hire.
  • Always send errors back as tool results (not silent failures) so the model can recover.
  • This single round trip is the building block the full agent loop (Ch. 14) repeats for multi-step tasks.

Understanding check
  1. Who actually executes a tool call — the model or your code? Your code — the model only requests a tool call with arguments; your application runs the real function and returns the result.
  2. Why does a vague tool description cause problems? The model decides when to use a tool almost entirely from its description, so a vague one leads to the tool being used at the wrong times or not at all.
