Embeddings Deep-Dive

General AI Eng the numerical representation that makes search-by-meaning possible

Why this matters. Every RAG system (Chapters 21-26) starts with the same question: "given a user's question, which of my 10,000 documents are actually relevant?" Keyword search misses paraphrases ("car" vs "automobile"). Embeddings solve this by turning text into vectors (Ch. 1 taught the basics) placed so that meaning-similar text ends up numerically close — this chapter goes deeper on how to actually pick and use them well.

🟢 In plain words. An embedding turns a piece of text into a list of numbers that captures its meaning. Text that means similar things gets similar numbers — so you can find related text by comparing numbers, instead of hoping the exact same words appear.
🔍 The tricky part, in plain language. An embedding is just a long list of numbers (a "vector") that captures the meaning of a piece of text as a point in space. Similar meanings land near each other even with zero shared words — "car" and "automobile" sit close together; "car" and "carpet" sit far apart despite sharing letters. The computer never compares words; it compares positions in this meaning-space by measuring the angle between two vectors (cosine similarity). Picture a giant library where books are shelved by topic instead of alphabetically, so related ideas end up on nearby shelves. Takeaway: embeddings turn the fuzzy question "do these mean the same thing?" into the exact question "are these two points close?" — which a computer can answer instantly.

Real-world analogy

Imagine every sentence gets plotted as a dot on a giant map, where dots close together mean similar meaning. "I love dogs" and "I adore puppies" land near each other; "I love dogs" and "the stock market fell" land far apart. An embedding model is the cartographer that decides where each dot goes — a better cartographer places dots more accurately, which is the whole game.

1. What an embedding model actually outputs

You give it text; it gives back a fixed-length list of numbers — a vector. That length is the model's dimensionality: common sizes are 384, 768, 1536, or 3072. More dimensions can capture more nuance, but cost more storage and are slightly slower to search — it's a real tradeoff, not "bigger is always better."

"The cat sat on the mat" │ ▼ embedding model [0.021, -0.184, 0.077, ..., 0.003] ← e.g. 1536 numbers (OpenAI text-embedding-3) "A feline rested on the rug" │ ▼ [0.019, -0.179, 0.081, ..., 0.006] ← very close to the vector above "Quarterly revenue grew 12%" │ ▼ [0.412, 0.033, -0.291, ..., 0.188] ← far from both of the above

2. Picking a model: what actually matters

FactorWhy it matters
DimensionalityHigher = potentially more nuance, but more storage + slower search. Many modern models offer Matryoshka embeddings — you can truncate to fewer dimensions and lose only a little accuracy.
Domain fitA general-purpose model trained mostly on web text may underperform on legal, medical, or code-heavy text — domain-specific or code-specific embedding models exist for a reason.
Max input lengthEvery model has a token limit for what it can embed in one call — this interacts directly with your chunking strategy (Ch. 22).
Cost & latencyYou'll call this on every document at ingest time and on every user query — cheap and fast matters at scale.
ConsistencyNever mix vectors from two different embedding models in one index — their number spaces aren't comparable, even if dimensions happen to match.

3. Generating embeddings — a real example

import Anthropic from "@anthropic-ai/sdk";
// Anthropic doesn't ship its own embedding model — pair Claude with a
// dedicated embedding provider (Voyage AI is Anthropic's recommended partner)
import { VoyageAIClient } from "voyageai";

const voyage = new VoyageAIClient({ apiKey: process.env.VOYAGE_API_KEY });

const result = await voyage.embed({
  input: ["The cat sat on the mat", "A feline rested on the rug"],
  model: "voyage-3",
  inputType: "document"   // "document" at ingest time, "query" at search time
});

const vectors = result.data.map(d => d.embedding);  // [[...], [...]]
Notice inputType. Many embedding models embed queries and documents slightly differently under the hood for better retrieval accuracy — always set this correctly, or you'll silently lose search quality.

4. Similarity metrics — how "closeness" is actually measured

MetricWhat it measuresNotes
Cosine similarityThe angle between two vectors, ignoring their lengthMost common default for text embeddings — it cares about direction (meaning), not magnitude
Dot productAngle and magnitude combinedFaster to compute; equivalent to cosine if vectors are pre-normalized to length 1 (most embedding APIs already do this)
Euclidean (L2) distanceStraight-line distance between the two pointsLess common for text; more typical in image/geometric embedding spaces
Cosine similarity ranges from -1 to 1 (often 0 to 1 for text): 1.0 → identical meaning 0.8 → very similar 0.3 → loosely related 0.0 → unrelated -1.0 → opposite meaning (rare in practice for text)

5. Common pitfalls

  • Mixing embedding models between ingest and query time — even a version bump can shift the vector space enough to break retrieval.
  • Embedding text that's too long — most models silently truncate past their max input length, quietly dropping the end of a document.
  • Forgetting to normalize — if you compute cosine similarity by hand instead of via the API, make sure you're dividing by vector magnitude correctly.
  • Assuming higher dimensions always win — test on your actual data; a smaller, domain-tuned model often beats a bigger general one.

Key takeaways

  • An embedding model turns text into a fixed-length numeric vector where meaning-similar text ends up numerically close.
  • Model choice depends on dimensionality, domain fit, max input length, cost, and — critically — consistency across your whole pipeline.
  • Cosine similarity is the standard metric for text; it compares direction (meaning), not magnitude.
  • Never mix vectors from different embedding models or versions in the same index.
  • Embeddings are the foundation the rest of Part 4 (chunking, vector stores, retrieval) builds on.

  1. Why can't you mix vectors from two different embedding models in one index? Each model places text in its own distinct vector space — the numbers aren't comparable across models, even if dimensions match, so similarity scores become meaningless.

💬 Conceptual questions (the kind interviewers ask)

Answer each out loud before peeking. These tie this chapter to real production concerns — cost, latency, failures, and safety.

  1. You embed 5 million chunks once, then embed every user query. Where's the cost, and how does dimensionality affect it?
    Ingest is a one-time bulk cost; every query is an ongoing per-request embedding call plus a search over all those vectors. Higher dimensions mean more storage and slightly slower search on every query — pick the smallest dimension that keeps accuracy (Matryoshka truncation helps).
  2. You upgrade your embedding model but only re-embed new documents. What silently breaks?
    Old and new vectors now live in different number spaces and aren't comparable — similarity scores become meaningless and retrieval quietly degrades. Any model or version change means re-embedding the entire index.
  3. Retrieval quality is poor on your legal corpus even with a big general-purpose model. Likely cause and fix?
    Domain mismatch — a general web-trained model blurs specialized legal terms. Try a domain- or code-specific embedding model, and test on your actual data rather than assuming bigger always wins.
  4. Why is cosine similarity the default for text, and why does inputType (query vs. document) matter?
    Cosine compares direction (meaning) while ignoring length — the right default for text. Setting inputType matches how the model was trained to encode queries vs. documents, quietly protecting retrieval accuracy.
