LangGraph

General AI Eng orchestrating agents as a graph — with loops, branches, state, and human checkpoints

Why this matters. A plain chain (Ch. 27) runs straight through: step A, then B, then C, done. But real agents need to loop ("use a tool, look at the result, maybe use another"), branch ("if unsure, go retrieve more"), remember state across steps, and sometimes pause for a human to approve. LangGraph is the tool for exactly that — it lets you draw your agent as a graph of nodes and edges, which is the honest shape of how agents actually think.

Real-world analogy

A chain is a factory conveyor belt: parts move one way, station to station, no going back. LangGraph is a board-game board: you have squares (nodes), and rules for which square you move to next (edges) — including "roll again," "go back three spaces," and "if you land here, the banker (a human) decides." That ability to loop and branch is the whole point.

1. The three words that make up a graph

TermWhat it isIn plain English
StateA shared object that every step can read and updateThe "shared notebook" the whole agent scribbles in — messages so far, retrieved docs, a counter
NodeA function that does one unit of work and updates the stateOne station: "call the model," "run a tool," "retrieve documents"
EdgeA rule for which node runs nextThe arrow between stations — can be fixed or conditional ("if X, go here; else there")
The key upgrade over chains. Edges can point backward. That single ability — an edge that loops a node back to an earlier one — is what turns a straight pipeline into a real agent that can keep trying until the job is done.

2. What a ReAct agent looks like as a graph

The classic agent loop from Ch. 19 (reason → act → observe → repeat) is just a tiny graph with one loop in it:

┌──────────────────────────────┐ │ │ ▼ │ ┌─────────┐ wants a tool? ┌──────────┐ │ model │ ───── yes ──────▶ │ tool │ │ node │ │ node │ └─────────┘ ◀───── result ────└──────────┘ │ │ no more tools needed ▼ END (final answer)

The conditional edge after the model node is the brain of the loop: it inspects the state and decides "the model asked for a tool → go to the tool node" or "the model gave a final answer → go to END." After the tool runs, a fixed edge sends control back to the model. That's a cycle — impossible with a plain chain.

3. The shortcut: create_react_agent

You rarely wire that loop by hand. LangGraph ships a prebuilt helper that builds the whole model↔tool loop for you — you just supply the model and the tools.

import { ChatAnthropic } from "@langchain/anthropic";
import { createReactAgent } from "@langchain/langgraph/prebuilt";
import { tool } from "@langchain/core/tools";
import { z } from "zod";

const model = new ChatAnthropic({ model: "claude-sonnet-4-6" });

// a tool = a function + a described schema so the model knows how to call it
const getWeather = tool(
  async ({ city }) => `It's 22°C and sunny in ${city}.`,
  {
    name: "get_weather",
    description: "Get the current weather for a city.",
    schema: z.object({ city: z.string() }),
  }
);

// this one call builds the entire reason→act→observe graph for you
const agent = createReactAgent({ llm: model, tools: [getWeather] });

const result = await agent.invoke({
  messages: [{ role: "user", content: "What's the weather in Tokyo?" }],
});
console.log(result.messages.at(-1).content);
What just happened. Under the hood, createReactAgent created exactly the graph in §2: a model node, a tool node, and the conditional edge that loops between them until the model stops asking for tools. You get the loop without drawing it.

4. Building a custom graph, by hand

When you need branching logic that isn't just "loop until done," you build the graph explicitly. The pattern is always the same three moves: define the state, add nodes, wire edges.

import { StateGraph, START, END, Annotation } from "@langchain/langgraph";

// 1. STATE — the shared notebook every node reads & writes
const State = Annotation.Root({
  question: Annotation<string>,
  context:  Annotation<string>,
  answer:   Annotation<string>,
});

// 2. NODES — each is just a function that returns a state update
async function retrieve(state) {
  const docs = await myRetriever.invoke(state.question);   // Part 4 RAG
  return { context: docs.map(d => d.pageContent).join("\n") };
}
async function generate(state) {
  const reply = await model.invoke(
    `Context:\n${state.context}\n\nQuestion: ${state.question}`
  );
  return { answer: reply.content };
}

// 3. WIRE the graph: START → retrieve → generate → END
const graph = new StateGraph(State)
  .addNode("retrieve", retrieve)
  .addNode("generate", generate)
  .addEdge(START, "retrieve")
  .addEdge("retrieve", "generate")
  .addEdge("generate", END)
  .compile();

const out = await graph.invoke({ question: "What is chunking?" });
console.log(out.answer);

5. Conditional edges — where the real power lives

A conditional edge is a function that looks at the state and returns the name of the next node. This is how you branch: retry on low confidence, escalate to a bigger model, or stop early.

// decide the next hop based on what's in the state
function routeAfterCheck(state) {
  if (state.confidence < 0.5) return "retrieve_more";  // loop back
  return "generate";                                    // move on
}

graph.addConditionalEdges("grade", routeAfterCheck, {
  retrieve_more: "retrieve",   // map return value → actual node
  generate: "generate",
});

6. The two features you can't get any other way

Checkpointing (durable memory)

Attach a checkpointer and LangGraph saves the state after every node. That gives you two things at once: (a) memory — resume a conversation later using a thread_id, and (b) durability — if the process crashes mid-run, it resumes from the last saved step instead of starting over. This is the "persistent state across sessions" the memory chapters hinted at, done properly.

Human-in-the-loop

Because state is saved between nodes, the graph can pause at a checkpoint, surface its current state to a human ("about to send this email — approve?"), and resume only after you say yes. This is the safe pattern for any agent that takes real-world actions — the same "confirm before the irreversible step" principle you've seen throughout this notebook, built into the framework.

7. Chain vs. graph — when to reach for which

Plain chain (Ch. 27)LangGraph
FlowStraight line, one directionLoops, branches, back-edges
StateData just passes throughShared, inspectable, persisted
Good forFixed pipelines (RAG-answer, summarize)Agents, retries, multi-step reasoning, approvals
Resume after crashNoYes, with a checkpointer
Human approval mid-runAwkwardBuilt in
Rule of thumb. If your flow is "A then B then done," a chain is simpler — don't reach for a graph. The moment you need "keep going until…", "if this then that", memory across sessions, or a human checkpoint, that's LangGraph's home turf.

Key takeaways

  • LangGraph models an agent as a graph: state (shared notebook), nodes (work steps), edges (what runs next).
  • Unlike chains, edges can loop back and branch — that's what makes a real reason→act→observe agent possible.
  • createReactAgent builds the standard model↔tool loop for you; build a custom StateGraph when you need your own branching.
  • Conditional edges route based on the current state — the mechanism behind retries, escalation, and early stopping.
  • Checkpointing gives durable memory and crash-resume; human-in-the-loop lets the graph pause for approval before risky actions.
