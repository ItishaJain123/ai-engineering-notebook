Guardrails

General AI Eng the safety checks around your model — validating what goes in and what comes out

Why this matters. A model will happily accept any input and produce any output — it has no built-in sense of your app's rules. Guardrails are the checks you add around the model: reject bad input before it reaches the model, and inspect the model's output before it reaches the user or a downstream system. This is the first chapter of Part 6 (going to production), and it's the difference between a demo and something you'd trust with real users.

Real-world analogy

Guardrails are the bouncer and the quality inspector of your app. The bouncer checks people at the door (input): no weapons, right age. The inspector checks products before they ship (output): nothing broken, nothing offensive. The model is the party inside — talented, but it needs someone at both doors making sure only safe things pass through.

1. Two gates: input and output

Every guardrail sits at one of two points in the flow. Get this mental picture and the rest follows:

user input │ ▼ [ INPUT GUARDRAIL ] ← reject/clean before spending a model call │ (too long? off-topic? contains an attack? disallowed request?) ▼ MODEL │ ▼ [ OUTPUT GUARDRAIL ] ← inspect before it reaches the user/database/API │ (valid JSON? leaked secrets? unsafe content? made-up facts?) ▼ user / next system

2. Input guardrails

CheckWhat it catches
Length / size limitsRunaway inputs that blow your token budget or hit context limits.
Topic / scope filteringA support bot being asked to write malware or do your taxes — keep it on-mission.
Injection detectionInputs trying to hijack your instructions ("ignore your rules and…") — the whole of Ch. 31.
Disallowed contentRequests for clearly banned categories, blocked before you even pay for a call.
PII in the inputUsers pasting sensitive data you shouldn't store — redact it first (Ch. 32).
Why check input before the model? It's cheaper (no wasted model call), faster (instant rejection), and safer (a bad prompt never reaches the model at all). Cheap deterministic checks first, expensive model calls only for what passes.

3. Output guardrails

CheckWhat it catches
Schema / format validationYou asked for JSON with fields {name, age} — verify it actually parses and matches before using it.
Safety / content filteringToxic, unsafe, or policy-violating text before a user ever sees it.
PII / secret leakageThe model echoing back an API key, password, or someone's personal data.
Grounding / hallucination checksIn RAG, verifying the answer is actually supported by the retrieved sources (Part 4).
Business rules"Never recommend a competitor," "never promise a refund" — your app's specific limits.

4. Three ways to implement a guardrail

TypeHow it worksTrade-off
Rule-based (code)Plain logic: regex, length checks, JSON schema validation, allow/deny listsFast, cheap, 100% predictable — but only catches what you explicitly wrote
Model-based (LLM judge)A second model call asks "is this input/output safe & on-topic?"Catches fuzzy, nuanced cases — but costs a call, adds latency, and can itself err
Dedicated classifiersPurpose-built safety/moderation models that score content for known categoriesFast and specialized — but another dependency to run and tune
Layer them. Real systems stack all three: cheap code checks first (reject the obvious), then a classifier or LLM judge for the subtle stuff. Never rely on a single guardrail — defense in depth is the whole idea.

5. Schema enforcement — the most common guardrail you'll write

The single most frequent output guardrail is "make sure the JSON is valid and shaped right." Validate it in code; if it fails, retry or fall back — never blindly trust model output feeding a database or API.

import { z } from "zod";

// define the shape you REQUIRE from the model
const Result = z.object({
  sentiment: z.enum(["positive", "negative", "neutral"]),
  score: z.number().min(0).max(1),
});

const raw = await callModel(userText);      // model returns a JSON string

const parsed = Result.safeParse(JSON.parse(raw));
if (!parsed.success) {
  // guardrail tripped — retry, ask again, or use a safe default
  return { sentiment: "neutral", score: 0.5 };
}
useIt(parsed.data);                          // now provably the right shape

6. What to do when a guardrail trips

Blocking is only half the job — you must decide the response. Design this deliberately:

  • Reject — return a safe canned message ("I can't help with that").
  • Retry — ask the model again, often with a corrective note ("return valid JSON only").
  • Sanitize — strip the offending part (e.g. redact PII) and continue.
  • Escalate — hand off to a human (ties back to human-in-the-loop, Ch. 28).
  • Log — always record the trip, so you can measure and improve (Ch. 34, observability).

Key takeaways

  • Guardrails are safety checks you add around the model — the model itself doesn't know your app's rules.
  • They sit at two gates: input (before the model, cheap to reject early) and output (before results reach users or systems).
  • Implement them three ways — rule-based code, model-based judges, dedicated classifiers — and layer them for defense in depth.
  • Schema validation is the everyday workhorse: never feed unvalidated model JSON into a database or API.
  • Always define what happens on a trip: reject, retry, sanitize, escalate — and log every one.
