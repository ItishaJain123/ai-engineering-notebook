Structured Output

General AI Eng forcing a model's free-form text into a schema your code can actually parse

Why this matters. A chatbot can reply in prose. A pipeline — something feeding data into a database, another API, or a UI component — needs the model's output in a fixed, predictable shape. Structured output is what turns "the model said something reasonable-sounding" into "the model returned {name: string, date: string, amount: number} that my code can safely use."

Real-world analogy

Asking a model "extract the invoice details" without a schema is like asking a new employee to "fill out the invoice form" without showing them the form — they'll write something reasonable, in their own layout, maybe missing a field, maybe using "USD 450" where you needed 450.00. Structured output is handing them the actual form with labeled boxes: now everyone fills it out the same way, every time.

1. The simplest approach: ask for JSON in the prompt

You can just ask nicely — describe the exact JSON shape you want in the system prompt. This works reasonably well but isn't guaranteed: the model might add commentary before the JSON, use inconsistent field names, or produce invalid JSON on an edge case.

const response = await client.messages.create({
  model: "claude-sonnet-5",
  max_tokens: 200,
  system: "Extract invoice details as JSON only, no other text. " +
          'Shape: {"vendor": string, "date": "YYYY-MM-DD", "amount": number}',
  messages: [{ role: "user", content: invoiceText }],
});
// Still need to parse and validate — the model *can* deviate
const data = JSON.parse(response.content[0].text);

2. The reliable approach: force it through a tool schema

The much more robust technique (this connects directly to Chapter 11, Tool Use) is to define a "tool" whose only purpose is to hold your desired output shape, and force the model to call it. Because tool inputs are validated against a JSON Schema by the API itself, this dramatically reduces malformed output compared to just asking in the prompt.

const response = await client.messages.create({
  model: "claude-sonnet-5",
  max_tokens: 200,
  tools: [{
    name: "record_invoice",
    description: "Record extracted invoice details.",
    input_schema: {
      type: "object",
      properties: {
        vendor: { type: "string" },
        date:   { type: "string", description: "ISO format YYYY-MM-DD" },
        amount: { type: "number" },
      },
      required: ["vendor", "date", "amount"],
    },
  }],
  tool_choice: { type: "tool", name: "record_invoice" }, // force this exact tool
  messages: [{ role: "user", content: invoiceText }],
});
const data = response.content.find(b => b.type === "tool_use").input;
// `data` is already a parsed object matching your schema — no JSON.parse needed
Prompt-only JSON vs. Tool-forced schema ───────────────────── ───────────────────── "please output JSON" input_schema validated by API Model *might* comply Model *must* match the schema You JSON.parse() + hope You get a typed object back Fails silently on edge cases API errors loudly if it can't comply

3. Validating with a schema library (Zod)

Even with tool-forced output, validate on your side too — schemas describe shape, not business rules (like "amount must be positive"). In JS, zod is the standard tool for this, and it's the same library used to define MCP tool schemas back in Chapter 4.

import { z } from "zod";

const InvoiceSchema = z.object({
  vendor: z.string().min(1),
  date: z.string().regex(/^\d{4}-\d{2}-\d{2}$/),
  amount: z.number().positive(),
});

const result = InvoiceSchema.safeParse(data);
if (!result.success) {
  // retry the API call, or route to a human review queue
  console.error("Invalid extraction:", result.error.issues);
} else {
  saveInvoice(result.data); // fully typed, validated
}

4. What to do when validation fails

StrategyWhen to use it
Retry with the validation error appended to the promptOccasional failures — telling the model exactly what was wrong often fixes it in one more turn
Lower temperature (Ch. 0c) toward 0If failures seem to come from unnecessary creative variation in formatting
Fall back to a stricter tool schema with fewer optional fieldsIf the model keeps omitting or misnaming specific fields
Route to human reviewHigh-stakes extraction (financial, medical) where silent bad data is unacceptable

Key takeaways

  • Asking for JSON in the prompt is easy but not guaranteed — the model can still deviate.
  • Tool-forced schemas (a tool whose only job is to hold your output shape, called via tool_choice) are the reliable way to get structured output from Claude.
  • Always validate the result against a real schema (e.g. zod) on your side — API-level shape validation doesn't check business rules.
  • Have a plan for validation failures: retry-with-error, stricter schema, or human review — don't let bad data pass silently.

Understanding check
  1. Why is a tool-forced schema more reliable than asking for JSON in plain text? The API validates the tool call's input against the JSON Schema you defined, constraining the model's output structurally rather than just hoping it follows a text instruction.
  2. Why validate again on your own side even after using a tool schema? Schemas enforce shape (types, required fields) but not business logic (e.g. a date must be in the past, an amount must be positive) — that still needs your own validation.
