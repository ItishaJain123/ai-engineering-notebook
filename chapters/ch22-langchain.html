Part 5 · Chapter 27

LangChain

General AI Eng the toolkit that glues models, prompts, memory, and tools into one pipeline

Why this matters. Everything you've built so far — calling a model, adding tools (Ch. 16), doing RAG (Part 4) — you wrote by hand, wiring each piece together yourself. LangChain is a framework that gives you ready-made building blocks for all of those pieces and a standard way to snap them together. You don't need it, but on a big project it can save you from re-inventing the plumbing. This chapter teaches you what it is, when it helps, and — just as importantly — when the native SDK you already know is the better choice.

Real-world analogy

Think of building a PC. You can buy each part loose — motherboard, RAM, cables — and wire it yourself (that's using the raw SDK). LangChain is like a barebones kit: the case, slots, and cables are pre-fitted and standardized, so you just drop parts in. The kit is faster to assemble and easy to swap parts in — but it also adds bulk you might not need for a simple build.

1. What LangChain actually is

LangChain is an open-source framework (available in Python and JavaScript/TypeScript) for building LLM-powered apps. Its core idea is to wrap every moving part of an AI app behind a standard interface, so you can mix and match without rewriting glue code:

Building blockWhat it wraps
ModelsA uniform way to call Claude, GPT, Gemini, a local model — swap providers by changing one line.
Prompt templatesReusable prompt strings with {placeholders} you fill in at runtime.
Output parsersTurn the model's raw text into structured data (JSON, a list, a typed object).
Retrievers & vector storesThe RAG pieces from Part 4, behind one interface — swap Chroma for Pinecone in one line.
MemoryAutomatically carry conversation history between turns.
Tools & agentsGive the model functions to call and let it loop (the agent pattern from Ch. 19).

2. The one idea that ties it together: chains

The name is literal. A chain is a sequence of steps where the output of one feeds the input of the next: prompt → model → parser. Modern LangChain expresses this with a pipe-style syntax (called LCEL, the LangChain Expression Language) that reads left to right.

user input │ ▼ [ prompt template ] fills "{question}" into a full prompt │ ▼ [ model ] sends it to Claude, gets a reply │ ▼ [ output parser ] extracts clean text / JSON │ ▼ final answer

3. A minimal chain in JavaScript

import { ChatAnthropic } from "@langchain/anthropic";
import { ChatPromptTemplate } from "@langchain/core/prompts";
import { StringOutputParser } from "@langchain/core/output_parsers";

// 1. the model — swapping to another provider is a one-line change
const model = new ChatAnthropic({ model: "claude-sonnet-4-6" });

// 2. a reusable prompt with a placeholder
const prompt = ChatPromptTemplate.fromTemplate(
  "Explain {topic} to a beginner in two sentences."
);

// 3. a parser that gives us plain text back
const parser = new StringOutputParser();

// 4. pipe them into one chain, then run it
const chain = prompt.pipe(model).pipe(parser);
const answer = await chain.invoke({ topic: "embeddings" });
console.log(answer);
Read the .pipe() calls. That's the whole philosophy: each stage is a Lego brick with the same shape of connector, so prompt.pipe(model).pipe(parser) just clicks them in order. Want to add RAG? Pipe a retriever in front of the prompt. Want JSON out? Swap the parser. Nothing else changes.

4. Memory & retrievers, for free-ish

Two things you built by hand earlier come pre-packaged:

  • Memory — instead of manually appending each turn to a messages array, LangChain can wrap your chain so history is stored and re-injected automatically every turn (in newer versions this lives in LangGraph, the subject of Ch. 28).
  • Retrievers — the entire Part 4 pipeline (embed the query → search the vector store → return top-k docs) becomes vectorStore.asRetriever(), one object you pipe into a RAG chain.

5. The honest part: overlap with native tool use

Here's the tension you should understand clearly. The Claude SDK already gives you tool calling, streaming, structured output, and a clean message API. So LangChain often wraps things you can already do directly — sometimes adding a helpful standard, sometimes adding a layer you have to learn and debug on top of the real thing.

Native SDK (what you know)LangChain
Learning curveJust the provider's APIThe API plus LangChain's abstractions
Swapping providersRewrite the callChange one line — big win if you switch a lot
DebuggingYou see the raw request/responseExtra layers can hide what's actually sent
Boilerplate on big appsYou write the glue (memory, RAG wiring)Pre-built blocks save real time
Best fitFocused apps, one provider, full controlComplex multi-component apps, many integrations, teams standardizing
Rule of thumb. Reach for LangChain when your app has many interchangeable parts (multiple models, several vector stores, lots of pre-built integrations) and you value a common vocabulary across a team. Stick with the native SDK when you want a small footprint, minimal dependencies, and to see exactly what hits the API. Neither is "more advanced" — they're different trade-offs.

6. Where it goes next: LangGraph

Simple chains run straight through: A → B → C, done. But real agents need to loop ("call a tool, look at the result, maybe call another"), branch ("if the answer is uncertain, retrieve more"), and pause for a human. Plain chains can't express those cleanly. That's exactly the gap LangGraph fills — and it's the next chapter.

Key takeaways

  • LangChain is a framework that wraps models, prompts, parsers, memory, retrievers, and tools behind standard interfaces so you can snap them together.
  • A chain pipes one step's output into the next: prompt → model → parser, written with .pipe().
  • Its biggest wins are swappability (change providers/stores in one line) and pre-built blocks that cut boilerplate on large apps.
  • It heavily overlaps with native tool use — the cost is an extra layer to learn and debug, so it's not automatically the right choice.
  • Use it for complex, many-part apps; prefer the native SDK for focused apps where you want full visibility and a small footprint.
