Subagents / Agent (Task) Tool

Claude Code how delegation works · when to delegate vs. do inline

Why this matters. A single agent's context window is finite (Chapter 2). Big jobs — "search the whole repo," "review 30 files" — would flood it. Subagents let the main agent spin up a helper with its own fresh context, hand it a task, and get back only a short summary. The bulk of the work never pollutes your main whiteboard.

Real-world analogy

You're a manager on a deadline. Instead of reading 500 pages yourself, you send an intern to read them and report back one paragraph. You stay focused; the reading happened elsewhere. The catch: briefing and debriefing the intern takes effort, so you only delegate when the task is big enough to be worth it.

How delegation works in Claude Code

  • The main agent calls the Agent (Task) tool, giving a subagent a type and a prompt.
  • The subagent runs its own plan→act→observe loop with a separate context window and its own tool set.
  • It cannot see your conversation; it only knows what you put in its prompt. Its final message is the only thing returned to the main agent (the user doesn't see its internal steps).
  • A fresh Agent call starts cold; some setups let you continue an existing subagent to reuse its context.

Built-in subagent types (examples)

TypeGood for
ExploreRead-only fan-out search across many files; returns conclusions, not file dumps
PlanDesigning an implementation strategy before coding
general-purposeMulti-step research/tasks when you're unsure where the answer lives

You can also define custom subagents (a Markdown file with name, description, allowed tools, and a system prompt) in .claude/agents/ — e.g. a "js-test-writer" specialist.

---
name: js-test-writer
description: Writes Vitest unit tests for JS modules. Use when asked to add tests.
tools: Read, Grep, Edit
---
You are a testing specialist. Given a module, write thorough Vitest tests
covering happy paths and edge cases. Follow existing test style.

When to delegate vs. do inline

Delegate to a subagentDo it inline
Wide search / reading many filesYou already know the file
Big result you only need summarizedYou need the raw detail in context
Parallelizable independent chunksTightly coupled, back-and-forth edits
Isolating a noisy task to protect contextQuick, small task (delegation overhead not worth it)
The core tradeoff: a subagent saves your context but costs a round-trip and loses shared state (it can't see your conversation). Delegate when context savings > briefing cost. For a two-line grep, just do it inline.

Two key limits

  • No shared memory. Everything the subagent needs must be in its prompt. Vague briefs → wrong results.
  • Only the final summary returns. Design the task so the useful output is that final message.

This is the CC-native version of multi-agent orchestration (Chapter 24): an orchestrator delegating to workers. Same pattern, bigger scale later.

Key takeaways

  • Subagents run in a separate context and return only a final summary.
  • Use them to keep heavy reading/search out of your main context window.
  • They can't see your conversation — brief them fully in the prompt.
  • Delegate when context savings beat the round-trip + briefing cost; otherwise inline.
  • Custom subagents live in .claude/agents/ with their own tools + system prompt.

  2. Draft the frontmatter (name + description + tools) for a custom subagent you'd want — e.g. "explain-diff" or "js-refactorer."
Understanding check
  1. Why does delegating a big repo search protect your main session? The subagent reads in its own context and returns a short summary; the raw content never enters your window.
  2. What's the main risk of a vague subagent prompt? It can't see your conversation, so missing context → wrong or incomplete results.
