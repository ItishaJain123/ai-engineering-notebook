Subagents / Agent (Task) Tool

Claude Code how delegation works · when to delegate vs. do inline

The one-line idea. A subagent is a helper AI you send off to do a chunk of work in its own separate workspace. It only reports back the final answer — not everything it did to get there.

Think of your chat as a whiteboard

Your conversation with Claude is like a whiteboard with limited space (Chapter 7). If you ask "search my whole codebase for every place X is used," reading 50 files onto that whiteboard fills it up fast — no room left for the work you actually care about. A subagent reads those 50 files on its own whiteboard, in a separate room, and hands you back one clean summary.

The manager & intern analogy

You're a manager on a deadline. Instead of reading 500 pages yourself, you send an intern to read them and come back with one paragraph. You never touch the 500 pages — your desk stays clear.

The catch: you have to brief the intern clearly, because they can't read your mind or see what's already in your head. And getting a paragraph back instead of doing it yourself takes a bit of extra time — so you don't send an intern to fetch you one coffee. Only worth it for big jobs.

How it actually works, step by step

  1. The main agent calls the Task tool, picks a subagent type, and writes it a prompt — the briefing.
  2. That subagent starts completely fresh. It has no idea what you and the main agent talked about — only what's in the prompt.
  3. It runs its own little loop (search files, read things, reason) in its own private context, with its own tools.
  4. When it's done, only its final message comes back. All its intermediate scratch-work disappears — you never see the 50 files it read, just the summary.

The 3 built-in types

TypeUse it for
Explore"Find X across the repo" — read-only search, returns conclusions not file dumps
Plan"Design how I'd build this" before writing any code
general-purposeAnything else multi-step, or when you're not sure where the answer lives

You can also build your own custom subagent — a specialist with its own name, job description, allowed tools, and instructions — saved as a Markdown file in .claude/agents/. Example: a "test writer" that only ever writes tests.

---
name: js-test-writer
description: Writes Vitest unit tests for JS modules. Use when asked to add tests.
tools: Read, Grep, Edit
---
You are a testing specialist. Given a module, write thorough Vitest tests
covering happy paths and edge cases. Follow existing test style.

When to delegate vs. just do it yourself

Send a subagentDo it inline instead
Big search / lots of files to readYou already know exactly which file
You only need a summary of a big resultYou need the raw detail yourself
Several independent chunks that can run in parallelTightly coupled, back-and-forth edits
Keeping a noisy task out of your main contextQuick, small task — not worth the overhead
Simple rule: a subagent saves your context but costs a round trip and can't see what you already know. Delegate when the context saved is worth more than the cost of briefing it. For a two-line lookup, just do it yourself.

🛠️ Step by step: build your own custom subagent

  1. Pick a scope. .claude/agents/ in your project (shared with the team via git) or ~/.claude/agents/ in your home folder (personal, works in every project you open).
  2. Create a Markdown file in that folder — the filename doesn't matter much, but name it after the agent, e.g. .claude/agents/code-reviewer.md.
  3. Write YAML frontmatter + a system prompt: 
    ---
name: code-reviewer
description: Reviews code for quality and best practices
tools: Read, Glob, Grep, Bash
model: sonnet
---

You are a senior code reviewer. When invoked:
1. Run `git diff` to see recent changes
2. Focus on modified files
3. Give feedback organized by priority (critical, warnings, suggestions)
  4. Know the key fields:
    FieldRequired?What it does
    nameYesHow you or Claude refer to it
    descriptionYesTells the main agent when to reach for this one
    toolsNoRestrict it to only the tools it needs — safer, more focused
    modelNoPick a cheaper/faster model for simple jobs, or omit to inherit
  5. Invoke it three ways: 
    // let Claude decide when to use it
"Use the code-reviewer to check my changes"

// force it directly
@code-reviewer

// make it the default for a whole session
claude --agent code-reviewer
No build step, no registration. Claude Code just reads the .claude/agents/ folder — save the file and it's immediately usable.

🛠️ Using the same subagent across multiple projects

Save it in your user-level folder instead of a project one:

~/.claude/agents/code-reviewer.md

Anything here is available in every project you open Claude Code in — no copying files around. A project-level one (.claude/agents/ inside a repo) only exists for that repo. If both a user-level and a project-level agent share the same name, the project-level one wins in that repo — handy for overriding your personal default on one specific project.

🛠️ How to pass it a prompt

The "prompt" is just whatever task text you give it when you invoke it — no separate config step.

  • Natural language (Claude decides when to delegate, writes the brief itself): 
    "Use the code-reviewer to check my changes for security issues"
  • Direct @-mention (you control exactly what it gets): 
    @code-reviewer review src/auth.js for SQL injection risks
    Everything after the mention becomes that subagent's entire prompt — its whole context. It can't see the rest of your conversation, so be as specific as you'd be briefing someone who just walked in.
  • From your own code (Agent SDK, Chapter 11): pass the prompt as a string param when spawning it, e.g. Agent({ description: "...", prompt: "Review src/auth.js for SQL injection, focus on the login handler at line 40" }).
Bad briefGood brief
"check the code""review src/auth.js, flag any place user input reaches a SQL query without parameterization, report file:line for each"
Remember: the more concrete detail in the prompt — file paths, what "done" looks like, what to ignore — the better the result, because it's the only input the subagent has.

🛠️ Agent View — watching multiple agents at once

So far each subagent you send off is quick — it runs, reports back, and you keep working. But what if you kick off several long-running background agents at once (e.g. one researching, one refactoring, one running tests)? You need a way to see all of them without losing your place.

That's Agent View — a terminal screen for monitoring and managing multiple parallel sessions/background agents:

claude agents
  • Shows a list of every running session — its status, a progress summary, and (if relevant) whether it's opened a PR yet.
  • You can peek at any agent's output without interrupting it.
  • You can reply to a specific agent, or attach to it to take over control directly.
  • You can start new background agents from here, or fork a session with /fork to try a different approach without losing the original.
Analogy: if a single subagent is one intern reporting back to you, Agent View is the manager's dashboard showing every intern currently out in the field — what they're doing, how far along they are, and a button to walk over and check on any one of them.
Agent View is for background/parallel agents specifically — a normal foreground subagent's output just streams straight into your current conversation, no separate view needed.

🛠️ Agent Teams — subagents that talk to each other

Everything above still has one property: a subagent reports back only to you (or the main agent) — subagents never talk to each other. Agent Teams (experimental) removes that limit: several Claude Code instances work together, with one acting as lead and the rest as teammates that communicate directly with one another, not just upward.

It's an experimental feature — enable it in your settings first:

// .claude/settings.json
{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  }
}

Then just ask, in plain language:

"Spawn 3 teammates to investigate this bug —
one testing the database hypothesis, one the API hypothesis,
one the client hypothesis. Have them challenge each other's findings."
SubagentsAgent Teams
Who they report toOnly the lead/main agentMessage each other directly, plus a shared task list
CoordinationLead manages every stepTeammates self-coordinate
CostLower — brief in, summary outHigher — every teammate is a full separate Claude instance
MaturityStable, everyday useExperimental — known limitations
Heads up: Agent Teams is still experimental — sessions with in-process teammates can't always be resumed, task status can lag, and teams can't be nested inside teams. Reach for a normal subagent first; use a team only when tasks genuinely need to debate or cross-check each other's findings.

The one thing to remember

Subagents are blind to your conversation. If your prompt to them is vague, their answer will be vague or wrong — because they have literally nothing else to go on. A good brief is the whole game.

This same pattern — one "manager" agent delegating to several "worker" agents — scales up into full multi-agent systems, which you'll see in Chapter 29.

Key takeaways

  • A subagent works in its own separate context and only returns a final summary.
  • Use one to keep heavy reading/search out of your main conversation.
  • It can't see your conversation — you must brief it fully in the prompt.
  • Delegate when the context you save beats the round-trip + briefing cost; otherwise just do it inline.
  • Custom subagents live in .claude/agents/ with their own tools and instructions.

Understanding check
  1. Why does delegating a big repo search protect your main conversation? The subagent reads everything in its own separate context; only its short summary comes back to you — the raw files never fill up your window.
  2. What's the biggest risk of a vague subagent prompt? It can't see your conversation, so anything you didn't explicitly tell it is invisible to it — leading to missing or wrong results.
