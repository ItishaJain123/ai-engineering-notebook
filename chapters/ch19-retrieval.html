Part 4 · Chapter 24

Retrieval Strategies

General AI Eng hybrid search and reranking — getting the right chunks, not just similar ones

Why this matters. Pure vector/semantic search (Ch. 21-23) is powerful — it finds meaning, not just matching words. But it isn't perfect. It can miss exact keyword matches: a product SKU like SKU-88213, an exact error code like ERR_CONN_RESET, or a person's name — things a plain keyword search would catch instantly, but that an embedding model might blur into "something about products" or "something about errors." Real production retrieval systems usually combine multiple strategies instead of relying on vector search alone.

🟢 In plain words. Search-by-meaning is great at paraphrases but can miss exact things like an order number or error code. Hybrid search runs meaning-search and keyword-search together; a reranker then carefully re-orders a cheap shortlist. You retrieve broad and cheap, then narrow and precise.
🔍 The tricky part, in plain language. Vector search matches on meaning, which is great for "how do I return an item?" but bad for exact strings like a product code SKU-88213 or a person's name — meaning-wise those are basically noise, so the right document may not rank near the top. The fix is hybrid: run a meaning search (vectors) and a keyword search (BM25, which literally matches the words), then combine them. After that, a reranker takes the ~50 candidates and re-scores them more carefully to float the best few to the top. Picture searching with both a "sounds like what I meant" filter and a "contains this exact word" filter, then having an expert re-sort the finalists. Takeaway: meaning-search and keyword-search miss different things — combine them, then rerank the shortlist.

Real-world analogy

Imagine house-hunting. Semantic search is telling an agent "find me neighborhoods that feel like this one I loved" — walkable, quiet, leafy. Keyword search is "it must have exactly 3 bedrooms and be under $500k" — no fuzziness allowed, exact match or nothing. A good agent uses both at once: narrow by the hard requirements, then rank by feel. Retrieval systems face the same split, and the best ones don't pick one — they combine them.

1. Three approaches to retrieval

ApproachHow it worksStrengthsWeaknesses

2. How hybrid search actually combines results

The query runs against both a keyword index and a vector index at the same time. Each returns its own ranked list. Those two lists then get merged into one combined ranking — usually via a weighted score (e.g. 0.5 * bm25_score + 0.5 * vector_score, after normalizing both to comparable ranges) or reciprocal rank fusion (RRF), which combines results based on their rank position in each list rather than raw scores, making it more robust when the two scoring scales don't line up well.

3. Reranking: a second, more careful pass

Initial retrieval (keyword, vector, or hybrid) is built for speed — it scans potentially millions of chunks and returns, say, the top 50 candidates fast but only approximately ranked. A reranker is a separate, more expensive model that looks directly at the query alongside each of those 50 candidates and re-scores them far more precisely — something too slow to run against the whole corpus, but perfectly affordable against a shortlist of 50.

Think of it as a two-stage funnel: cheap and broad first, then expensive and precise on a small shortlist.

Stage 1 — retrieve (cheap, broad) 10,000+ chunks ──► hybrid search ──► top 50 candidates Stage 2 — rerank (expensive, precise) top 50 candidates ──► reranker model ──► top 5, precisely ordered (scores query + each candidate together)
// conceptual — actual SDK/API shape varies by reranker provider
const initialResults = await hybridSearch({
  query: userQuestion,
  topK: 50   // cast a wide net cheaply
});

const reranked = await rerank({
  query: userQuestion,
  documents: initialResults,   // only 50 candidates — affordable to score precisely
  topK: 5                      // keep only the best few
});

// reranked[0] is now the model's best guess at the single most relevant chunk
The practical order of operations end-to-end:
  1. Hybrid retrieve — combine keyword + vector search to pull ~50 candidate chunks, cheaply and broadly.
  2. Rerank — run those 50 through a reranker model to precisely re-score and cut down to the top ~5.
  3. Generate — pass only those top 5 chunks into the LLM's context window for the final answer.

4. Is the extra complexity worth it?

SituationRecommendation
Small dataset (hundreds to low thousands of chunks), precision isn't critical, prototypingPlain vector search is enough — skip hybrid + reranking, keep it simple
Large dataset, exact terms matter (IDs, codes, names, legal/medical text), precision-critical use case, production systemUse hybrid search + reranking — the added complexity pays for itself in answer quality

A good rule of thumb: add complexity when you can point to a real failure mode it fixes. If users are asking about exact order numbers or specific error codes and vector search keeps missing them, that's your signal to add a keyword layer and a reranker — not before.

Key takeaways

  • Vector search alone can miss exact-term matches like codes, SKUs, and names — keyword (BM25) search catches those instantly.
  • Hybrid search runs both and fuses the ranked lists, usually via weighted scoring or reciprocal rank fusion (RRF).
  • Reranking is a second, more expensive pass that re-scores only a small shortlist (e.g. top 50) for much more precise final ordering.
  • The practical pipeline is a funnel: retrieve broad and cheap (~50) → rerank precise and narrow (~5) → send only those to the LLM.
  • Skip the complexity for small, low-stakes datasets; add it when precision on exact terms genuinely matters at scale.

Understanding check
  1. Why can vector search alone fail on a query containing a specific product SKU? Embeddings capture meaning/similarity, not exact tokens — a specific code or ID can get blurred into "something roughly similar" rather than matched exactly, which is exactly what keyword/BM25 search is built to catch.
  2. Why is reranking applied only to a small shortlist (e.g. top 50) rather than the whole corpus? Rerankers score the query together with each candidate directly, which is far more accurate but also far more computationally expensive — cheap enough for 50 candidates, way too slow to run against millions of chunks.
💬 Conceptual questions (the kind interviewers ask)

Answer each out loud before peeking. These tie this chapter to real production concerns — cost, latency, failures, and quality.

  1. A user searches for "SKU-88213" and vector search misses the exact document. Why, and what fixes it?
    Embeddings blur exact codes into "roughly about products" rather than matching the precise token. Keyword/BM25 search catches exact tokens instantly — run both (hybrid search) so you catch codes and paraphrases.
  2. Why rerank only the top ~50 candidates instead of your whole corpus?
    A reranker scores the query together with each candidate — very accurate but expensive. It's affordable on 50 candidates and hopelessly slow on millions. That's the point of the funnel: cheap-and-broad retrieval first, expensive-and-precise reranking on the shortlist.
  3. When is hybrid search + reranking not worth the added complexity?
    On small, low-stakes datasets (a few hundred chunks) where plain vector search already works — two indexes, a fusion step to tune, an extra reranker call, and added latency don't pay for themselves. Add complexity only to fix an observed failure.
  4. How does the fusion step combine two ranked lists, and why might you prefer RRF?
    Weighted scoring blends the two normalized scores; reciprocal rank fusion (RRF) combines by rank position, which is more robust when the keyword and vector scoring scales don't line up. Either way you get one merged ranking to feed the reranker.
