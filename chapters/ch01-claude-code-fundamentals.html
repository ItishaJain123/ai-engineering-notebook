Part 1 · Chapter 1

Claude Code Fundamentals

Claude Code CLAUDE.md · slash commands · hooks · settings · permission modes

Why this chapter exists. Raw Claude Code has two gaps: (1) it doesn't know your project, and (2) it's powerful, so you need control over what it does automatically. Nearly every feature here solves one of those two problems — keep that lens as you read.

Real-world analogy

Think of Claude Code as a brilliant new contractor you just hired:
  • CLAUDE.md = the onboarding doc ("here's how we do things here").
  • Slash commands = saved shortcuts for tasks you request repeatedly.
  • Settings = the employee handbook / configuration.
  • Permission modes = their keycard access level.
  • Hooks = automatic office rules that always fire ("every time you touch the code, run the linter").

1. CLAUDE.md — project memory

A plain Markdown file Claude auto-reads at the start of every session. Put durable facts here so you never repeat yourself: stack, commands, style, gotchas.

# Project: My App

## Commands
- Build: `npm run build`
- Test:  `npm test`
- Lint:  `npm run lint`

## Conventions
- JavaScript (ES modules), never TypeScript here.
- API routes live in `src/routes/`.
- Never commit directly to `main`.

Locations (most specific wins): project root ./CLAUDE.md (team-shared) → subdirectory CLAUDE.md (folder-specific) → global ~/.claude/CLAUDE.md (all your projects). Create one fast with the /init command, which scans the repo and drafts it.

Good CLAUDE.md hygiene: keep it short and high-signal. It's loaded into context every session, so bloat costs tokens on every turn. Facts, not essays.

2. Slash commands — reusable prompts

Saved prompts invoked with /name, stored as Markdown in .claude/commands/. Built-ins exist, and you write your own.

Reference: common built-in slash commands

These ship with Claude Code itself (not ones you write). Run /help any time to see the exact live list for your installed version — commands do get added/renamed over time.

/modelSwitch which model Claude Code uses for the session
/agentsView/manage available subagents (Chapter 5)

Reference: handy keyboard shortcuts

ShortcutWhat it does

/resume vs. /clear vs. /compact: these three get confused because they all touch "the conversation," but they do opposite things. /clear throws history away to start a new task. /compact shrinks history but keeps going on the same task. /resume goes the other direction — it brings old, already-ended sessions back so you can continue them later.
<!-- .claude/commands/review-pr.md -->
Review the current git diff for bugs, security issues, and style.
Group findings by severity. Suggest concrete fixes.

Now typing /review-pr runs that prompt. You can pass arguments with $ARGUMENTS and even run shell inside the command. It's a saved macro for work you repeat.

3. Settings — configuration (settings.json)

JSON files controlling permissions, environment variables, hooks, and model. Three levels of precedence:

FileScopeCommitted?
~/.claude/settings.jsonYou, everywhereNo
.claude/settings.jsonThis project, whole teamYes
.claude/settings.local.jsonThis project, just youNo (gitignored)
{
  "permissions": {
    "allow": ["Bash(npm run test:*)", "Read(*)"],
    "deny":  ["Bash(rm -rf *)"]
  }
}

4. Permission modes — how much it does without asking

Controls the approval prompts. Cycle modes with Shift+Tab.

ModeBehaviorUse when
defaultAsks before edits & commandsNormal work
acceptEditsAuto-accepts file edits; still asks for commandsYou trust the edit plan, want speed
planRead-only; proposes a plan, changes nothing until you approveBig or risky changes; research first
bypassPermissionsAsks for nothing ("yolo")Sandboxes/throwaway only — dangerous

5. Hooks — automatic, deterministic rules

Shell commands the harness runs automatically at lifecycle events (PreToolUse, PostToolUse, Stop, etc.). Key insight: a hook is guaranteed code, not a polite request to the model. If you need the linter to run after every edit, a hook guarantees it; a line in CLAUDE.md only asks nicely.

{
  "hooks": {
    "PostToolUse": [{
      "matcher": "Edit|Write",
      "hooks": [{ "type": "command", "command": "npm run lint --silent" }]
    }]
  }
}

Because the harness (not the model) executes hooks, they're how you enforce “from now on, every time X, do Y.” A hook's output/exit code can even block a tool call.

The one mental model to keep

There is a spectrum from suggestion → guarantee:

CLAUDE.md (usually followed) → slash command (you choose to invoke) → permission settings (Claude cannot cross) → hook (always runs)

When you want a behavior, ask: “Does this need to be guaranteed, or just encouraged?” That answer picks the tool.

Key takeaways

  • CLAUDE.md = auto-loaded project memory; keep it short and high-signal.
  • Slash commands = saved, reusable prompts for repeated tasks.
  • Settings live at user / project / local levels (local overrides project overrides user).
  • Permission modes trade safety for speed; plan mode is read-only research.
  • Hooks are deterministic guarantees run by the harness — use them for “always do X”.
  • Mental model: suggestion → guarantee. Pick the weakest tool that still guarantees what you need.
  • Built-in commands worth knowing beyond the basics: /resume (reopen an old session), /cost, /mcp, /agents, /permissions, /model — run /help for the full live list.

Understanding check (try before peeking)
  1. Core difference between a rule in CLAUDE.md vs. a hook?
    CLAUDE.md is a suggestion the model usually follows; a hook is deterministic code the harness always runs.
  2. Research a big change but touch no files until approved — which mode?
    Plan mode.
  3. You closed your terminal yesterday mid-task and want that exact conversation back — which command?
    /resume — /clear would erase it, /compact only shrinks an active session.
