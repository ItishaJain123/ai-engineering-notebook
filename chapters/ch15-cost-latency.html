Part 3 · Chapter 20

Cost & Latency Optimization

General AI Eng making an LLM-powered feature affordable and fast enough for production, not just a demo

Why this matters. A prototype that costs $2 and takes 20 seconds per request is fine for a demo. At real usage volume, that same design can bankrupt a product or make it feel broken. This chapter pulls together concepts from earlier in Part 3 (tokens, caching, streaming) into a practical playbook for keeping an LLM feature both cheap and fast.

🟢 In plain words. Match the tool to the job. Don't send every request to your biggest model, don't re-pay for context you already sent, and don't make users wait for work that could run overnight. Get those three right and you've done most of cost and latency work.
🔍 The tricky part, in plain language. Almost everything about cost and speed comes down to one word: tokens (roughly word-pieces). You pay per token, and time is spent per token. Two things to know: input tokens (your prompt) are cheaper than output tokens (the model's reply), and output tokens are the big driver of latency because the model generates them strictly one at a time. Picture paying by the word and waiting while each word of the reply is written out by hand — a 5,000-token prompt is read almost instantly, but a 5,000-token answer is produced slowly, word by word. Takeaway: to cut cost, shrink the prompt; to cut latency, shrink the output (or stream it so it at least feels faster).

Real-world analogy

Think of model calls like hiring consultants. You wouldn't hire your most expensive, most thorough consultant to answer "what time is it in Tokyo" — you'd ask a receptionist. Cost/latency optimization is mostly about matching the tool to the task: expensive/careful only where it's actually needed, cheap/fast everywhere else.

1. Model routing — don't use your biggest model for everything

Different tasks need different amounts of capability. A classification task ("is this email spam?") doesn't need the same model as "write a nuanced legal analysis." Routing simple, high-volume tasks to a smaller/faster/cheaper model — and reserving the most capable model for genuinely hard steps — is often the single biggest cost lever available.

Naive: every request → biggest, most expensive model ┌──────────────────────────────────────────────┐ │ "Is this a support ticket about billing?" │ ← simple, high volume │ "Draft a legal risk memo for this contract" │ ← complex, low volume └──────────────────────────────────────────────┘ both hit the same expensive model 😬 Routed: match model to task difficulty "Is this about billing?" → smaller/faster model ✅ cheap, fast "Draft a legal risk memo" → largest/most capable ✅ worth the cost

2. Token budgeting

Every token — in your prompt and in the reply — costs money and adds latency (Ch. 1). The main levers:

LeverHow it helps
Trim unnecessary contextDon't send an entire document when only one section is relevant (this is part of why RAG, Ch. 21-26, exists)
max_tokens caps (Ch. 3)Prevents an unexpectedly long reply from blowing the budget on one request
Prompt caching (Ch. 15)Avoids re-paying full price for large, repeated context on every call
Concise system promptsA bloated, redundant system prompt costs tokens on every single request — worth trimming ruthlessly

3. Batching

If you have many independent, non-urgent requests (e.g. classifying 10,000 support tickets overnight), batch APIs process them asynchronously at a significant cost discount compared to real-time calls — the tradeoff is you get results later (often within hours), not instantly.

Real-time API: 1 request → 1 response, immediately, full price Batch API: 10,000 requests → submitted together → processed async → results ready later → substantial cost discount Use batch when: no one is waiting live for the individual answer

4. Latency: where the time actually goes

Latency sourceWhat helps
Time to first tokenStreaming (Ch. 18) — doesn't reduce total time, but the user sees output sooner
Total generation timeSmaller max_tokens, smaller/faster model, avoiding unnecessary extended thinking (Ch. 17)
Repeated large-context reprocessingPrompt caching (Ch. 15)
Multi-step agent loops (Ch. 19)Fewer unnecessary tool calls, parallelizing independent steps where possible

5. Retries and fallbacks

Production systems need to handle rate limits (too many requests too fast) and transient errors gracefully — not by hanging or crashing, but with a sensible retry strategy.

async function callWithRetry(fn, maxRetries = 3) {
  for (let attempt = 0; attempt < maxRetries; attempt++) {
    try {
      return await fn();
    } catch (err) {
      if (err.status === 429 && attempt < maxRetries - 1) {
        // rate limited — back off exponentially before retrying
        await new Promise(r => setTimeout(r, 2 ** attempt * 1000));
        continue;
      }
      throw err; // not retryable, or out of attempts
    }
  }
}

6. Putting it together: a checklist

  • Am I using the smallest/cheapest model that reliably handles this specific task? (model routing)
  • Is there large, repeated context I'm re-paying for on every call? (prompt caching, Ch. 15)
  • Is my system prompt bloated with anything non-essential? (token budgeting)
  • Does this need to be real-time, or could it run as an overnight batch? (batching)
  • Am I streaming where perceived latency matters to a real user? (Ch. 18)
  • Do I have retry/backoff logic for rate limits, instead of failing outright?

Key takeaways

  • Model routing — matching task difficulty to model size — is usually the biggest cost lever available.
  • Token budgeting (trimmed context, caps, caching, lean system prompts) reduces both cost and latency together.
  • Batch APIs trade immediacy for a significant cost discount on large, non-urgent workloads.
  • Streaming improves perceived latency; smaller models/outputs and fewer agent steps reduce actual latency.
  • Production systems need retry/backoff logic for rate limits — don't let a 429 error take down a whole pipeline.

💬 Conceptual questions (the kind interviewers ask)

This is the chapter interviewers probe hardest — the classic "your AI is in production, now make it work" questions. Answer each out loud before peeking.

  1. An AI agent in production is too slow. Walk through where the bottlenecks are.
    Four places: time-to-first-token (helped by streaming, Ch. 18); total generation time (smaller model, smaller max_tokens, less extended thinking, Ch. 17); repeated large-context reprocessing (prompt caching, Ch. 15); and the number of serial agent steps / tool calls (cut or parallelize them, Ch. 19). Measure first — don't guess which one it is.
  2. What tradeoff would you make between latency/cost and quality, and how do you decide?
    Route by stakes: a cheap/fast model for high-volume simple steps, the best model only where being wrong is costly. Decide it with evals (Ch. 33) — measure how much quality the cheaper option actually loses, and accept it only if it still clears your bar.
  3. How would you cut the cost of a high-traffic feature without hurting users?
    Model routing (the biggest lever), prompt caching for shared context, lean system prompts, max_tokens caps, and batching anything that isn't real-time. Attack the largest, most-repeated source of tokens first.
  4. What happens when the model API actually fails in production, and how do you design for it?
    Rate limits (429s) and transient errors will happen. Handle them with exponential backoff/retries, a fallback model or cached/degraded response, request timeouts, and circuit breakers so one failing dependency doesn't cascade. Never let a 429 take down the whole pipeline.
