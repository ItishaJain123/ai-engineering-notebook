Prompt Engineering

General AI Eng the highest-leverage skill in this whole curriculum — steering a model's behavior with words alone

Why this matters. You don't retrain the model (Ch. 0b) and you don't fine-tune it for most tasks — you write a prompt. Prompt engineering is simply the practice of writing that prompt well enough that the model reliably does what you want, on the first try, every time. It's cheap to iterate on, and it's the first lever you should pull before reaching for anything more complex (RAG, fine-tuning, more tools).

Real-world analogy

Think of the model as a brilliant new hire on day one — extremely capable, but with zero context about your company, your preferences, or what "good" looks like for this specific task. A vague prompt is like saying "handle the customer emails" and walking away. A well-engineered prompt is a proper onboarding doc: here's your role, here's the format we expect, here are two examples of great work, here's what to do when you're unsure.

1. The four ingredients of a strong prompt

IngredientWhat it does
Role / system promptSets who the model is being for this task ("You are a senior code reviewer...") — shapes tone and priorities for the whole conversation
TaskThe specific, concrete instruction — the more specific, the less room for the model to guess wrong
FormatExactly how you want the output shaped (bullet list, JSON, a specific length) — don't assume the model will guess your preferred format
Examples (few-shot)1–3 worked examples of ideal input → output — often more effective than paragraphs of instructions

Never add commentary." │ ├─────────────────────────────────────────────────────────┤ │ FEW-SHOT EXAMPLES (2-3 input→output pairs) │ │ Input: "Meeting Tues 3pm with Sam" → │ │ Output: {"date":"Tuesday","time":"15:00","with":"Sam"} │ ├─────────────────────────────────────────────────────────┤ │ ACTUAL TASK (the real user input) │ │ "Lunch Friday noon with the design team" │ └─────────────────────────────────────────────────────────┘ │ ▼ Model has seen the pattern 2-3 times → follows it reliably

2. System prompt vs. user message

The system prompt sets standing behavior for the whole conversation (role, tone, rules that shouldn't change turn to turn). The user message is the actual, specific ask. Mixing them up is a common beginner mistake — putting task-specific instructions in the system prompt makes them harder to change per-request; putting persistent rules in every user message is repetitive and wastes tokens (see prompt caching, Ch. 10, for why that also costs money).

import Anthropic from "@anthropic-ai/sdk";
const client = new Anthropic();

const response = await client.messages.create({
  model: "claude-sonnet-5",
  max_tokens: 300,
  system: "You are a senior code reviewer. Be direct and specific. " +
          "Flag bugs and security issues first, style nits last. " +
          "Never say 'looks good' without giving at least one concrete observation.",
  messages: [
    { role: "user", content: "Review this function:\n\n" + codeSnippet }
  ],
});

3. Few-shot examples: show, don't just tell

Telling the model "respond concisely" is weaker than showing it two concise responses. The model pattern-matches on structure far more reliably than it follows abstract adjectives like "concise," "professional," or "friendly" — those words mean different things to different people, and the model has to guess which meaning you intend.

const messages = [
  { role: "user", content: "Summarize: 'The quarterly report shows revenue up 12%...'" },
  { role: "assistant", content: "Revenue +12% QoQ, driven by enterprise segment." },
  { role: "user", content: "Summarize: 'Customer churn increased due to pricing changes...'" },
  { role: "assistant", content: "Churn up — pricing changes cited as primary driver." },
  // Now the real task — model has seen the exact output shape twice
  { role: "user", content: "Summarize: '" + longReportText + "'" },
];

4. Chain-of-thought: let it think before it answers

For anything involving multi-step reasoning (math, logic, multi-part analysis), asking the model to reason step-by-step before giving a final answer measurably improves accuracy — it gives the model "room" to work through the problem instead of jumping straight to a guess. (Extended thinking, Ch. 12, is a more structured, built-in version of this same idea.)

Weak prompt: "What's 17% of 340, minus half of 58?" → model may jump straight to a (sometimes wrong) number Chain-of-thought: "Work through this step by step, then give the final answer on its own line: What's 17% of 340, minus half of 58?" → 17% of 340 = 57.8 half of 58 = 29 57.8 - 29 = 28.8 Final answer: 28.8

5. Common mistakes

MistakeFix
Vague adjectives ("be helpful", "be smart")Give concrete, checkable instructions ("cite the source for every claim")
No format specifiedState the exact output shape, or provide a schema (Ch. 9)
Burying the real task under paragraphs of preamblePut the most important instructions first and last — models weight both ends of a long prompt more heavily
One giant prompt for everythingSplit distinct behaviors into different system prompts / calls rather than one prompt trying to do it all

Key takeaways

  • A strong prompt has four ingredients: role, task, format, examples — examples are often the highest-leverage of the four.
  • System prompt = standing behavior for the whole session; user message = the specific ask — don't mix them up.
  • Few-shot examples teach output shape more reliably than abstract instructions like "be concise."
  • Chain-of-thought prompting ("think step by step") improves accuracy on multi-step reasoning tasks.
  • Prompt engineering is the cheapest lever to pull — try it before reaching for RAG, fine-tuning, or more tools.
🎯 Your exercise
  1. Take a vague prompt like "write a product description" and rewrite it with all four ingredients (role, task, format, one example).
  2. Test the same math/logic question with and without "think step by step" — compare accuracy.
  3. Reflect: why might putting critical instructions at both the start and end of a long prompt help, rather than just once?
Understanding check
  1. Why are few-shot examples often more effective than descriptive instructions? The model pattern-matches on concrete structure more reliably than it interprets subjective adjectives like "professional" or "concise," which can mean different things.
  2. What's the difference between a system prompt and a user message? System prompt sets standing role/behavior for the whole conversation; user message is the specific, per-turn request.
