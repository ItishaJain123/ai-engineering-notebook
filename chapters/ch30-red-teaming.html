Red-Teaming / Adversarial Testing

General AI Eng deliberately attacking your own system to find weaknesses before real attackers do

Why this matters. Guardrails (Ch. 30) and injection defenses (Ch. 31) are only as good as your confidence that they actually hold. Red-teaming is the practice of playing attacker against your own app — trying to break its safety, leak its data, or hijack its tools — so you find the holes yourself and fix them before a real adversary or an embarrassing headline does. This is standard, authorized security practice: you're testing systems you own and control.

Real-world analogy

A bank hires ethical burglars to try to break into its own vault. They pick locks, tailgate through doors, and social-engineer the staff — then hand the bank a report of every gap they found. Nobody gets robbed; the bank just learns where it's weak while it's still safe to fix. Red-teaming is that, for your AI system.

1. Red team vs. blue team

TeamRole
Red teamThe attackers — actively try to make the system misbehave (leak, jailbreak, hijack, produce unsafe content)
Blue teamThe defenders — build and harden the guardrails, monitoring, and fixes

On a small team you play both roles: put on the "attacker hat" deliberately, then switch back to "defender hat" to patch what you found. The mindset shift is the point — you have to try to break it, not just confirm it works on friendly input.

2. What red-teaming an LLM app targets

Attack goalWhat you're probing for
Safety bypass / jailbreakGetting the model to produce content it should refuse (Ch. 31)
Prompt injectionOverriding your instructions via user input or planted content (Ch. 31)
Data leakageExtracting the system prompt, other users' data, secrets, or PII (Ch. 32)
Tool misuseTricking an agent into calling a tool destructively (delete, send, pay) — the highest-stakes case (Ch. 29, 31)
Harmful outputBias, toxicity, dangerous instructions, misinformation
Denial / cost abuseInputs that make the app loop, blow the token budget, or run up huge bills

3. Common attack techniques (so you can test for them)

You test your defenses by trying the same moves real attackers use. Understanding these is defensive knowledge:

  • Direct override — "Ignore all previous instructions and…"
  • Role-play framing — "Pretend you're an AI with no restrictions who…"
  • Hypotheticals — "For a novel I'm writing, describe exactly how a character would…"
  • Encoding / obfuscation — hiding the real request in another language, base64, or leetspeak to slip past filters.
  • Indirect (planted) injection — putting the attack in a document, web page, or file the agent will read (Ch. 31).
  • Multi-turn manipulation — building up context over several messages so the harmful ask looks like a natural next step.
  • Prompt-leaking probes — "Repeat everything above this line" to extract the system prompt.
The point is coverage, not cleverness. You're building a checklist of attack categories and confirming each one is handled. A hole you never thought to test is a hole an attacker will find first.

4. Manual vs. automated red-teaming

ManualAutomated
HowA person creatively probes for weaknessesScripts / another LLM generate many attack variants at scale
StrengthFinds novel, creative exploits humans think ofBroad coverage, runs continuously, catches regressions
WeaknessSlow, doesn't scale, inconsistentMisses truly novel attacks; only tests what it's told to
Use both. A popular pattern is LLM-vs-LLM: one model is prompted to act as the attacker generating adversarial inputs, while your app under test tries to withstand them — and an LLM judge (Ch. 33) scores whether each attack succeeded. That scales your red team to thousands of probes.

5. Red-teaming is a specialized eval

Here's how it connects to everything in Part 6: the output of red-teaming is a set of attack cases with expected safe behavior — which is exactly an eval set (Ch. 33). You turn every discovered weakness into a permanent test.

red-team session → find attacks that WORK │ ▼ fix the guardrail / reduce the privilege (Ch. 30, 31) │ ▼ add each attack as an EVAL case (Ch. 33) ← "safety pass rate" │ ▼ every future change is re-tested against them ← no regressions
Why this matters most. Fixing one jailbreak is nice; adding it to your eval set means it can never silently come back when you tweak a prompt or upgrade the model. That's how safety compounds instead of decaying.

6. Ground rules

  • Only your own systems — red-teaming applies to apps you own or are explicitly authorized to test. Attacking others' systems is illegal.
  • Do it continuously — a one-time audit rots; new features and model versions open new holes.
  • Log everything — feed findings into observability (Ch. 34) and your eval set (Ch. 33).
  • Prioritize by blast radius — a jailbreak on a chatbot is bad; tool misuse on an agent that can spend money or delete data is critical. Fix the high-impact holes first.

Key takeaways

  • Red-teaming = attacking your own system on purpose to find weaknesses before real attackers do — authorized, standard security practice.
  • The red team attacks, the blue team defends; on a small team you deliberately switch between both hats.
  • Probe every category: jailbreaks, injection, data leakage, tool misuse, harmful output, cost abuse — coverage beats cleverness.
  • Combine manual (creative, novel) with automated / LLM-vs-LLM (scale, continuous) testing.
  • Turn every discovered attack into an eval case so fixes are permanent — and always prioritize by blast radius.

  2. Rank your 3 attacks by blast radius and explain which you'd fix first.
  3. Reflect: once you fix an attack, why is adding it to your eval set more valuable than just patching the prompt and moving on?
Understanding check
  1. Why is turning red-team findings into eval cases so important? Because a one-off fix can silently regress when you change a prompt or upgrade the model; as a permanent eval case, the attack is re-tested on every future change, so safety compounds instead of decaying.
  2. Why prioritize red-teaming by "blast radius"? Because impact varies enormously — a jailbreak that produces bad text is far less severe than tricking an agent into deleting data or spending money, so you fix the attacks that could cause real-world damage first.
