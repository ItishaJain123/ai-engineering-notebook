PII Redaction & Data Governance

General AI Eng keeping sensitive personal data out of places it shouldn't go

Why this matters. Your app will handle personal data — names, emails, phone numbers, card numbers, health info. Once that data flows into prompts, logs, third-party APIs, and vector stores, it's easy to leak it or store it somewhere you legally shouldn't. PII redaction (removing/masking sensitive data) and data governance (rules for how data is handled) are how you stay safe and compliant. This is table-stakes for any real product touching user data.

Real-world analogy

Think of a hospital handling patient files. Before a chart goes to a researcher, a clerk blacks out the patient's name and ID so the study can proceed without exposing who it is. Redaction is that black marker; governance is the whole set of hospital rules about who may see what, where files are stored, and how long they're kept. Your AI app needs both.

1. What counts as PII

PII = Personally Identifiable Information: anything that can identify a specific person, alone or combined with other data.

CategoryExamples
Direct identifiersFull name, email, phone, home address, SSN / national ID, passport number
FinancialCredit-card numbers, bank account numbers
Sensitive categoriesHealth records, biometrics, race, religion, sexual orientation (often extra-protected by law)
Quasi-identifiersBirth date, ZIP code, job title — individually harmless, but combined they can pinpoint someone

2. Where PII leaks in an LLM app

user message (may contain PII) │ ├──▶ sent to the model provider's API ← leaves your servers │ ├──▶ written to LOGS for debugging ← sits in plaintext for months │ ├──▶ embedded & stored in a VECTOR DB ← PII now searchable forever (Part 4) │ └──▶ echoed back in the model's OUTPUT ← shown to the wrong user
The sneaky ones are logs and vector stores. Everyone remembers the API call; few remember that debug logs and RAG indexes quietly accumulate PII for a very long time. Those are the places compliance audits find problems.

3. The core technique: detect, then de-identify

Redaction is two steps: find the PII, then replace it. There are several ways to replace it, and the choice matters:

MethodWhat it doesReversible?
MaskingReplace with a placeholder: [EMAIL], ****1234No — data is gone
Tokenization / pseudonymizationSwap real value for a fake token, keep a secure mapping to restore it laterYes — for you, with the key
HashingOne-way transform; same input → same hash (lets you match without storing the raw value)No
GeneralizationBlur precision: age 34 → "30–40", full ZIP → first 3 digitsNo

4. How to detect PII

  • Regex / pattern rules — great for structured formats: emails, phone numbers, card numbers (which even have a checksum you can validate). Fast, cheap, but misses names and free-form mentions.
  • NER models (Named Entity Recognition) — ML models trained to spot people, places, and organizations in free text; catch what regex can't.
  • Dedicated PII tools — libraries/services (e.g. Microsoft Presidio) combine both and handle many entity types out of the box.
  • An LLM itself — you can ask a model to find and tag PII, useful for nuanced cases — but it's slower, costs a call, and shouldn't be your only line.

5. Redact before the model, restore after (if needed)

A common safe pattern: strip PII from the text before it ever leaves your servers, let the model work on the placeholders, then swap real values back into the final result if the user is authorized to see them.

// 1. detect & replace PII with tokens, keeping a private map
const { clean, map } = redact(userText);
// userText: "Email John at john@acme.com"
// clean:    "Email [PERSON_1] at [EMAIL_1]"
// map:      { "[PERSON_1]": "John", "[EMAIL_1]": "john@acme.com" }

// 2. the model only ever sees the de-identified text
const reply = await callModel(clean);

// 3. if the end user is authorized, restore real values locally
const finalReply = restore(reply, map);
Why this is powerful. The model provider, your logs, and your traces only ever see [EMAIL_1] — never the real address. The mapping stays on your secured servers. Even a leak downstream exposes nothing.

6. Data governance — the rules around the redaction

Redaction is a tool; governance is the policy that decides when and how to use it. The pillars:

PrincipleWhat it means in practice
Data minimizationOnly collect & send what you actually need. The safest PII is the PII you never handled.
Access controlWho (and which service) can see raw vs. redacted data — enforce least privilege.
Retention limitsDelete data (and logs!) after a defined period — don't keep it "just in case."
Right to deletionLaws like GDPR/CCPA let users demand their data be erased — including from your vector store.
Audit trailsRecord who accessed what, so you can prove compliance (connects to observability, Ch. 34).
Data residencySome data legally must stay in a specific country/region — know where your provider processes it.
Not legal advice. Regulations (GDPR, HIPAA, CCPA, and others) are real legal obligations that vary by region and industry. This chapter teaches the engineering patterns; for what the law requires of your product, involve a qualified professional.

Key takeaways

  • PII is any data that can identify a person — including quasi-identifiers that only reveal identity in combination.
  • PII leaks through four doors: the provider API, logs, vector stores, and model output — logs and vector stores are the most-forgotten.
  • Redaction = detect (regex + NER + tools) then de-identify (mask, tokenize, hash, generalize) — pick reversible vs. not deliberately.
  • The strong pattern is redact before the model, restore after — providers and logs never see real values.
  • Governance wraps it in policy: minimize, control access, limit retention, honor deletion, keep audit trails, respect residency.

Understanding check
  1. Why is "redact before sending to the model, restore after" a strong pattern? Because the provider, your logs, and traces only ever see placeholders — never the real values — so a leak anywhere downstream exposes nothing, while the private mapping stays on your secured servers.
